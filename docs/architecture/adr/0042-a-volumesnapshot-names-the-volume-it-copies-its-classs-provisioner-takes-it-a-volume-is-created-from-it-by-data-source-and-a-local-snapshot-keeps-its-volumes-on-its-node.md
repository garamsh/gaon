# ADR 0042: A VolumeSnapshot names the Volume it copies, its class's provisioner takes it, a Volume is created from it by data source, and a local snapshot keeps its Volumes on its Node

> Status: accepted
> Date: 2026-11-13

Drafted for garamsh/gaon#247, part of goal #117, whose decision D7 is the PM's. It amends [ADR 0013](./0013-a-volume-is-created-through-its-own-path-a-local-volume-is-a-disk-its-nodes-agent-makes-and-a-binding-pins-it-to-a-node.md) in three places: a `local` Volume may carry a `dataSource` (its Decision 2 made it empty), a Volume may be pinned by its creation as well as by a binding (Decisions 1 and 3), and the agent deletes a disk only once no snapshot of it is waiting (Decision 4). It uses the provisioners of [ADR 0041](./0041-a-storageclass-names-the-provisioner-that-serves-its-volumes-says-whether-they-may-grow-and-the-local-class-is-one-the-api-server-creates.md) and the condition pattern of [ADR 0040](./0040-a-volumes-storage-may-grow-when-its-class-allows-it-the-provisioner-grows-the-disk-and-a-growth-still-open-shows-as-a-resizing-condition.md), and leaves the plugin API of [ADR 0019](./0019-the-node-agent-reaches-its-network-and-storage-plugins-as-separate-processes-through-a-versioned-grpc-api-on-unix-sockets.md) as it is. This ADR is the contract; serving it in the API server, the node agent and `storage-local` are later issues of #117.

## Context

- **A Volume had no copy.** A `local` Volume is one disk on one Node (ADR 0013), growth was added by ADR 0040, and nothing could keep the disk's state at a moment or start a new disk from it. `VolumeSpec.dataSource` is a string that ADR 0013 requires empty for `local` and leaves unchecked for any other class.
- **mvmd can now snapshot a disk.** The statements in this list hold for garamsh/mvmd at commit `29ce9e35b190a7819901ab8738b30a886edef5a1`, read as its ADR 0056 (`docs/architecture/adr/0056-a-node-local-disk-is-snapshotted-into-a-file-beside-the-disks-and-a-new-disk-is-created-from-a-snapshot.md`) and `docs/architecture/runtime-api.md`:
  - `SnapshotDisk {disk_id, snapshot_id, request_id}`, `ListDiskSnapshots` and `DeleteDiskSnapshot {snapshot_id}` exist, and `CreateDisk` takes `from_snapshot_id`. The client chooses the snapshot identifier, which obeys the rules of a disk identifier.
  - A snapshot is a file in `disk-snapshots/` of the node's state directory, a reflink of the disk's file where the file system has reflinks and a sparse copy where it has not. The node does not start when `disks/` and `disk-snapshots/` are on different file systems. Nothing in the API moves a snapshot between nodes, and ADR 0056 lists "Clients need a snapshot to move between nodes" among its signs of being wrong.
  - A repeat with the same snapshot identifier, request ID and disk succeeds and makes nothing again. A `CreateDisk` repeat with `from_snapshot_id` succeeds even after the snapshot was deleted.
  - A disk no Machine holds, or one a Created, Stopped or Paused Machine holds, is copied as it is. A Running Machine's disk is copied with the Machine paused, and the Machine is returned to Running; if it cannot be, the Machine is Faulted. A Faulted holder, or any other state, is precondition failed. The snapshot of a Running Machine's disk is crash-consistent and the guest is not asked to flush.
  - A disk made from a snapshot is a copy of the snapshot's file with its filesystem. A size below the snapshot's is invalid, a larger size grows the new file, and the guest grows the filesystem at the Machine's next Start. An unknown snapshot is not found.
  - `ListDiskSnapshots` reports, for each snapshot, the disk it was taken from, its size, its filesystem, the bytes it occupies and when it was taken.
  - `DeleteDiskSnapshot` of an absent snapshot succeeds, and of one a `SnapshotDisk` or `CreateDisk` call is using is precondition failed. Deleting the source disk does not touch its snapshots, and deleting a snapshot does not touch a disk made from it.
  - A disk is held for the duration of a `SnapshotDisk` call: no attach, delete or resize takes it meanwhile. What mvmd answers to a `SnapshotDisk` of a disk that is being grown is not stated.
  - The "snapshot" that mvmd's ADR 0055 says is not restorable after a growth, and that ADR 0040 and [resource-api.md](../resource-api.md) §Open questions repeat, is a Machine snapshot: a restore refuses a disk whose size differs from the Machine snapshot's record (`runtime-api.md` at the commit above). A disk snapshot is another object and has no such record.
- **The semantics follow Kubernetes' documentation, read on 2026-11-13**, "Volume Snapshots", <https://kubernetes.io/docs/concepts/storage/volume-snapshots/>, through a text extraction of the page. The footer reads "Last modified July 30, 2026". What was read: the lifecycle (dynamic provisioning, binding, "PersistentVolumeClaim as Snapshot Source Protection", deletion), the `VolumeSnapshot` example with `spec.source.persistentVolumeClaimName` and `volumeSnapshotClassName`, and "Provisioning Volumes from Snapshots". What was not read: the `status` fields, the size a restored volume needs, and any statement about consistency; `readyToUse` and `restoreSize` are taken from the issue's description of Kubernetes (#247), not from the page. What was taken:
  - a snapshot is an object of its own, taken from a claim by name, and a new volume is pre-populated from it by the `dataSource` of its claim;
  - a snapshot is made through a class, `volumeSnapshotClassName`, and "If nothing is set, then the default class is used if available";
  - "removal of the PersistentVolumeClaim object is postponed until the snapshot is readyToUse or aborted", so a source in use is not removed while a snapshot is taken from it;
  - deleting the `VolumeSnapshot` triggers the deletion of the underlying storage snapshot, under the `DeletionPolicy` of the content (`Delete` or `Retain`).
- **What the page does not state, and so is not taken as Kubernetes' behaviour:** whether a snapshot survives the deletion of its source after it is ready, the status of a refused restore, and how a restored claim whose snapshot does not exist behaves.
- **Where gaon departs from Kubernetes on purpose:**
  - there is no claim: a snapshot names a Volume, `spec.volumeName`, where Kubernetes' names a claim in `spec.source`; with one source kind there is no `source` union, and with no pre-provisioned snapshot there is no `VolumeSnapshotContent` kind;
  - a snapshot has no class (Decision 6);
  - a snapshot of the `local` class is **node-local**, which a snapshot of network storage need not be: it lives on one Node, and a Volume made from it must be on that Node (Decision 3). A `local` snapshot is as durable as that Node's state directory and is not a backup;
  - a Volume that names a snapshot that cannot be used yet is refused at creation, where Kubernetes leaves a claim pending (Decision 3 says why).

## Decision

**A `VolumeSnapshot` is a cluster-scoped object that names a Volume; the provisioner of that Volume's class takes the snapshot and reports it in `status`; a Volume is created from a ready snapshot by naming it in `spec.dataSource`, at least as large as the snapshot, and a `local` Volume so made is pinned at its creation to the Node that holds the snapshot.**

1. **The kind.** `VolumeSnapshot` of `compute.gaon.garam.sh/v1alpha1`, cluster-scoped, plural `volumesnapshots`, with a `spec` and a `status`:
   - `spec.volumeName`, required: the name of the Volume to copy, a lowercase DNS subdomain. It is **immutable**: an update that changes it is `Invalid`. The Volume need not exist at creation (Decision 2).
   - `status.readyToUse`: true once the snapshot exists whole and may be restored from.
   - `status.restoreSize`: the size of the snapshot, the smallest size of a Volume made from it. Set with `readyToUse`.
   - `status.storageClass`: the `spec.storageClass` of the source Volume when the snapshot was taken. Set with `readyToUse`.
   - `status.nodeName`: the Node that holds the snapshot, for a class whose snapshots are node-local. Set with `readyToUse`; required for the class `local`.
   - `status.conditions`, with the type `Snapshotting` (Decision 2).
   - Once `readyToUse` is true, a status write may not set it false or change `restoreSize`, `storageClass` or `nodeName`: a Volume may have been pinned by them.
2. **Who takes it, and how it shows.** The provisioner of the class of the source Volume (ADR 0041 Decision 4, as ADR 0040 Decision 4 assigns growth) takes the snapshot when it finds a `VolumeSnapshot` with `readyToUse` false whose source Volume it serves, and writes the result through `PUT /volumesnapshots/{name}/status`.
   - **`local`:** `storage-local`, on the Node the source Volume is pinned to, under the Node's identity, acts on a snapshot whose source Volume has `spec.nodeName` that Node and a `status.capacity`. It adds the finalizer `compute.gaon.garam.sh/node-agent` to the snapshot, asks mvmd to `SnapshotDisk` the Volume's disk, reads the size from `ListDiskSnapshots`, and writes `readyToUse` true with `restoreSize` that size, `storageClass` `local` and `nodeName` its Node, removing the `Snapshotting` condition in the same write. The finalizer is added before the first call, so a snapshot file never exists without it. The mvmd snapshot identifier is derived from the snapshot's `metadata.uid` and its request ID is the same on every attempt, so a repeat after a failure finds what the first made; the form is the serving issue's.
   - **Any other class:** the cluster-side provisioner of ADR 0041 takes the snapshot however its storage system does and writes the same fields, with `nodeName` empty unless its snapshots are node-local.
   - **A snapshot of a Volume that is in use.** A Running holder's disk is copied with the Machine paused, and the Machine may be Faulted if it cannot be resumed (mvmd at the commit above). gaon does not stop, stage or flush anything: the snapshot is crash-consistent, and a user who needs more stops the MicroVM or syncs in the guest first.
   - **How a snapshot not yet ready shows.** The provisioner keeps a condition of `type` `Snapshotting` and `status` `True`, with a `reason` and a `message`, from its first attempt until it writes `readyToUse` true. For `local` the reasons are:
     - `InProgress`: the request is taken and not finished;
     - `SourceNotReady`: the source Volume is pinned to this Node and has no `status.capacity` yet, because its disk does not exist;
     - `HolderNotSnapshottable`: mvmd answered precondition failed, as for a Faulted holder;
     - `Failed`: any other answer, with mvmd's message in `message`.
   - Every state is retried at each resync. The way out of a `Failed` snapshot is to delete it. There is no `phase`: `readyToUse` and the condition are the whole of the state.
   - **A snapshot with no one to take it** (the source Volume does not exist, is not pinned to a Node, or is of a class no provisioner serves) stays not ready with no condition, as a Volume of a class with no provisioner stays `Pending` (ADR 0041). It is not refused at creation, for the reason ADR 0041 Decision 2 gives: a Volume and its snapshot are written independently.
3. **Creating a Volume from a snapshot.** `spec.dataSource` of a Volume of any class is the name of a VolumeSnapshot. It is set at creation and immutable after, as all of `spec` is but `storage`. The API server reads the snapshot in a create that carries a `dataSource`, and:
   - a snapshot that does not exist is `Invalid`, as a binding that names a Volume that does not exist is (ADR 0013 Decision 3);
   - a snapshot that is not `readyToUse`, or has `deletionTimestamp` set, is `Conflict`: the state of another object, which may be retried;
   - a `spec.storageClass` other than the snapshot's `status.storageClass` is `Invalid`: the snapshot is the provisioner's copy of a disk of its class;
   - a `spec.storage` below the snapshot's `status.restoreSize` is `Invalid`. A size equal to it or above it is accepted, and mvmd grows a new disk to a larger size at its creation, the guest growing the filesystem at the Machine's next Start (mvmd at the commit above). Where that interval ends is not shown, as ADR 0040 says of a growth;
   - for the class `local`, the API server sets `spec.nodeName` to the snapshot's `status.nodeName` and adds the finalizer `compute.gaon.garam.sh/node-agent`, in the write that creates the Volume, as a binding does for a Volume it pins (ADR 0013 Decision 3). A user still may not carry a `nodeName` in a create. A Volume of another class is not pinned by this.
   - **Which Node, and why in the create.** An mvmd snapshot is a file on one Node and `CreateDisk` with `from_snapshot_id` can only run there, so a `local` Volume made from it can be on no other Node. The pin is how ADR 0013 already ties a Volume to a Node, and the scheduler already places a MicroVM on the Node of the Volumes it uses; pinning at creation uses both and changes neither. The Volume's disk is then made at once, with no MicroVM that uses it, by `storage-local` on that Node: `CreateDisk` with the snapshot's mvmd identifier and `spec.storage` bytes, a disk with the snapshot's filesystem, and `status.capacity` set as for any disk.
   - A Volume from a snapshot is otherwise a Volume: `local` still has `accessModes` exactly `ReadWriteOnce` and a positive `storage`, and may later grow (ADR 0040).
   - **A `local` Volume's `dataSource` is no longer `Invalid`, from the change that serves `Volume.CreateFromSnapshot`.** Until then `Volume.Validate` keeps refusing it, because the API server applies `Validate` on create and nothing yet applies the snapshot's checks or makes the disk from it: `storage-local` would make an empty disk and report no error. The API server's serving issue drops the refusal, in the change that applies `CreateFromSnapshot` and teaches `storage-local` to make the disk from the snapshot, and that change also updates [node-agent.md](../node-agent.md). `lib/api` holds the checks, as it holds `ValidateResize` for growth (ADR 0040).
4. **Deletion.**
   - **Deleting a snapshot.** `DELETE` sets `deletionTimestamp`, and the object is removed once its last finalizer is. The provisioner deletes the underlying snapshot, which for `local` is `storage-local` calling mvmd's `DeleteDiskSnapshot` (an absent snapshot is a success, and one an mvmd call is using is retried), and then removes its finalizer through `PUT /volumesnapshots/{name}`, by compare-and-swap and changing only its own entry. A snapshot never taken has no finalizer, so `DELETE` removes it at once.
   - **A snapshot a Volume still needs.** The provisioner removes the finalizer only when no Volume that names the snapshot in `spec.dataSource` is without a `status.capacity` and without `deletionTimestamp`, because that Volume's disk is not made yet and needs the snapshot. This holds the deletion of the snapshot, not the creation of a Volume, and is the snapshot's counterpart of the protection Kubernetes gives a source claim. A Volume whose disk is made no longer depends on the snapshot, and deleting the snapshot does not touch it (mvmd at the commit above).
   - **Deleting the source Volume.** The snapshot is not deleted and stays usable: mvmd's snapshot survives its disk (at the commit above). The disk is held meanwhile, as Kubernetes holds a source claim "until the snapshot is readyToUse or aborted": `storage-local` deletes the disk of a Volume with `deletionTimestamp` set, and so removes its `node-agent` finalizer, only once no VolumeSnapshot whose `spec.volumeName` is the Volume, and whose source is on its Node, is both not ready and not being deleted. A snapshot that fails for ever therefore holds a deleting Volume until the user deletes the snapshot; ADR 0013 already accepts finalizers that hold a Volume.
   - **A Node that is lost for good** takes its snapshots and the Volumes pinned to them with it. A `local` snapshot is not a backup.
5. **A snapshot and a growth of its source.**
   - A growth of the source after the snapshot does not touch the snapshot, whose size is `restoreSize`. A Volume made from it is as large as its `spec.storage` says, at least `restoreSize`, however large the source has become.
   - A snapshot taken while a growth is open records the disk's size, not `spec.storage`: `restoreSize` is what mvmd reports for the snapshot. mvmd holds a disk for a `SnapshotDisk` call and takes no resize meanwhile; the answer of the later call is an error that shows as `Failed` on the `Snapshotting` or the `Resizing` condition and is retried at the next resync (ADR 0040 Decision 5).
   - The open question that a snapshot is not restorable after a growth is closed for VolumeSnapshot: it was about a Machine snapshot, which gaon does not expose (Context).
6. **No snapshot class now.** Kubernetes' `VolumeSnapshotClass` carries the driver, a deletion policy and parameters. In gaon the driver is the class of the source Volume, whose StorageClass names the provisioner (ADR 0041); that class has no parameters or reclaim policy, and no provisioner has asked for either for a snapshot; the deletion policy is `Delete` always, as ADR 0013 chose for a Volume. A snapshot class would be a kind and a field with no reader. It is added by the issue of the first provisioner that needs a per-snapshot parameter or a policy other than `Delete`, and until then it is an open question in [resource-api.md](../resource-api.md).
7. **Who may write it.**
   - Users write `spec` at creation and delete snapshots, under `gaon:admin`'s `*`; no role for users is added. `spec` is immutable, so an `update` of a snapshot by anyone changes only metadata.
   - **The Node authorizer** allows a Node to read VolumeSnapshots, because a list cannot be filtered by Node; and to write the `status`, and the finalizer entry through `PUT /volumesnapshots/{name}`, of a VolumeSnapshot whose `status.nodeName` is that Node or whose source Volume has `spec.nodeName` that Node. The API server checks that only the finalizer entry changed, as it does for a Volume.
   - **A cluster-side provisioner's role**, which the administrator binds (ADR 0041), also holds `get`, `list` and `watch` on `volumesnapshots`, `update` on `volumesnapshots/status` and `update` on `volumesnapshots` for its finalizer. As for Volumes, the rule language cannot limit these to one class, so a provisioner so bound can write every snapshot's `status` and finalizers.
   - **The bootstrap roles** are unchanged: `gaon:scheduler` reads `volumes`, whose `spec.nodeName` the creation sets, and needs no snapshot; `gaon:controllers` reads and deletes every resource and writes no snapshot `status`.
8. **Client.** `lib/api` has `VolumeSnapshot`, `VolumeSnapshotList`, `VolumeSnapshotSpec` and `VolumeSnapshotStatus`, the constants `KindVolumeSnapshot`, `KindVolumeSnapshotList` and `VolumeSnapshotConditionSnapshotting`, and for the snapshot `Validate`, `ValidateUpdate`, `ValidateStatus` and `ValidateStatusUpdate`; and for a Volume `Volume.CreateFromSnapshot`, which holds the rules of Decision 3. No client method is added; they come with the serving issues.

## Consequences

- **A disk can be kept and branched**, with a reflink or a sparse copy, and the user writes two objects to do it. Nothing is enforced until the API server serves it: the contract and the library validate, and the documents describe what the server will do, as ADR 0013 said of itself.
- **A restored Volume lands where its snapshot is.** A user who wants to restore on another Node cannot; the way out is a copy by the user. A snapshot lives and dies with its Node's state directory.
- **A Volume and its snapshot cannot be applied in one stream before the snapshot is ready.** The Volume's create is `Conflict` and the user retries; waiting is not built. Creation order is a rule here, where ADR 0041 refused one for a class, because the Node is the snapshot's and the pin is made once, in the write.
- **A restore with a larger size** has a filesystem as small as the snapshot's until the guest grows it at the next Start.
- **The agent now reads VolumeSnapshots** and the Volumes that name them, and `storage-local` makes a disk for a Volume with no MicroVM. No call is added to the plugin API of ADR 0019: a provisioner learns of a snapshot from what it reads through the resource API, as it learns of a growth.
- **A source Volume's deletion can wait on its snapshots,** and a snapshot's deletion on the Volumes made from it before their disks exist. Both wait for objects the user owns.
- **A snapshot of a running workload pauses it** for the copy and may Fault it, as mvmd says; the contract does not stop that.
- **Rejected: leaving `nodeName` empty at creation and pinning at the binding.** The scheduler would have to read the snapshot to choose the Node, a binding to any other Node would be `Conflict` for ever, and the disk would wait for a MicroVM.
- **Rejected: accepting a Volume whose snapshot is absent or not ready and waiting `Pending`, as Kubernetes leaves a claim.** `spec.nodeName` is written by the API server or a binding and never by a Node (ADR 0013), so a waiting Volume would need a second writer of `nodeName` once the snapshot is ready.
- **Rejected: a typed `dataSource` of kind and name.** ADR 0013 made it a string, one kind exists, and a second would be a decision with its own ADR; cloning a Volume is not in mvmd.
- **Rejected: a `VolumeSnapshotContent` kind and pre-provisioned snapshots.** There is no snapshot that gaon did not take, and the one-to-one binding would be an object with a lifecycle and no reader.
- **Rejected: refusing to delete a snapshot a Volume names.** It would hold a snapshot for ever after the Volume's disk exists, when nothing depends on it.
- **Rejected: a second finalizer on the Volume for its snapshots.** The provisioner's wait before deleting the disk already holds it, and a second finalizer would add a writer.
- **Rejected: stopping the MicroVM to take a consistent snapshot.** A workload's run state is the user's, as ADR 0040 says of a growth.

## Signs the decision was wrong

- Users want to restore on a Node other than the snapshot's, or to keep a snapshot when its Node is lost, and ask for a snapshot that moves, which mvmd does not offer.
- Users apply a Volume and its snapshot together and retry the create by hand more often than they wait, and ask for the Volume to wait.
- Snapshots are taken of running workloads that Fault, and users ask for gaon to stage or flush first.
- Snapshots stay not ready with no condition because no provisioner runs, and users ask for something to say so.
- A provisioner needs a parameter or a deletion policy for a snapshot and has nowhere to read it.
- Source Volumes stay terminating because a snapshot of them fails.
