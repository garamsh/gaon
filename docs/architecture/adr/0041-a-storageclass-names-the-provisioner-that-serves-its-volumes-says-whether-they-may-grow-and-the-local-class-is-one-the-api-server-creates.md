# ADR 0041: A StorageClass names the provisioner that serves its Volumes, says whether they may grow, and the local class is one the API server creates

> Status: accepted
> Date: 2026-11-13

Drafted for garamsh/gaon#230, part of goal #117, whose decision D7 is the PM's. It amends [ADR 0013](./0013-a-volume-is-created-through-its-own-path-a-local-volume-is-a-disk-its-nodes-agent-makes-and-a-binding-pins-it-to-a-node.md), where `local` was a name `lib/api` knew and no object. It follows goal #117 D7 ("a `StorageClass` kind names a provisioner, which is a cluster-side extension") and D1 (a cluster-side extension is a client of the resource API with its own certificate identity and RBAC binding), and it leaves [ADR 0019](./0019-the-node-agent-reaches-its-network-and-storage-plugins-as-separate-processes-through-a-versioned-grpc-api-on-unix-sockets.md) as it is: that ADR's storage plugin is the Node-side process that attaches a disk to a MicroVM and serves `local`, and it is not the provisioner of another class. The growth a class allows is [ADR 0040](./0040-a-volumes-storage-may-grow-when-its-class-allows-it-the-provisioner-grows-the-disk-and-a-growth-still-open-shows-as-a-resizing-condition.md)'s. This ADR is the contract; serving the kind, creating the `local` class and the plugin's reads are later issues of #117.

## Context

- **A class was a string.** `spec.storageClass` of a Volume names a class, `lib/api` validates the one value `local`, and any other value is accepted and waits `Pending` for a plugin that serves it (ADR 0013). There is no object to say that a class exists, which plugin serves it, or whether its Volumes may grow, and ADR 0040 needs the last of these.
- **Two kinds of process touch storage.** The storage plugin of ADR 0019 is a Node-side process an agent names by `--storage-plugin <name>`, one per agent; it acts as its Node through the Node authorizer and its `StorageService.Attach(microvm)` returns the disks a MicroVM is created with. `storage-local` is that plugin for `local`, and it also makes, grows and deletes the disks of `local` Volumes (ADR 0013). A cluster-side extension (goal #117 D1) is a client of the resource API with a certificate identity and an RBAC binding, not a Node.
- **The rule language cannot narrow by class.** A `ClusterRole` rule names `apiGroups`, `resources` and `verbs`, and may carry a `labelSelector` that is judged on the labels of the object ([resource-api.md](../resource-api.md) §RBAC, ADR 0018). It has no field by which a rule selects Volumes by `spec.storageClass`, and a Volume's labels are written by the user who creates it.
- **Kubernetes' StorageClass** ("Storage Classes", <https://kubernetes.io/docs/concepts/storage/storage-classes/>, footer "Last modified October 29, 2026", the introduction and "Volume expansion" read) is an object with a `provisioner`, `parameters`, `reclaimPolicy`, `allowVolumeExpansion`, `mountOptions`, `volumeBindingMode`, and `allowedTopologies`; it has no `spec`, and a class's `provisioner` and parameters are immutable after creation, while `allowVolumeExpansion` may change.
- **mvmd's statements** in this ADR hold for garamsh/mvmd at commit `20150e3ba4dcc7bd860c3d80cb94ee44fd2227ed`: a disk is a file mvmd's Driver makes and grows, and nothing in mvmd knows of a class. `local` is the class gaon's `storage-local` serves with those disks.

## Decision

**A StorageClass is a cluster-scoped object with a `provisioner`, the name of the extension that serves its Volumes, and `allowVolumeExpansion`; a Volume names it by `spec.storageClass`; the class `local` is created by the API server at start and served on the Node by `storage-local`; and any other provisioner is a cluster-side extension that serves the Volumes of its class as a client of the resource API.**

1. **The kind.** `StorageClass` of `compute.gaon.garam.sh/v1alpha1`, cluster-scoped, with the fields of Kubernetes' that gaon uses and no `spec` and no `status`, as a ClusterRole has none:
   - `provisioner`, required: the name of the provisioner that serves the class, matching `[a-z0-9]([a-z0-9-]*[a-z0-9])?`. It is **immutable**: an update that changes it is `Invalid`. Deleting a class and creating another of the name is the way to change it.
   - `allowVolumeExpansion`, a boolean, false when omitted. It may change, and ADR 0040 says what it allows. Turning it off leaves a growth already written standing, as in Kubernetes; the provisioner finishes it.
2. **How a Volume names it.** `spec.storageClass` is the class's name, as now, and is required. A Volume whose class does not exist is accepted at creation, as now, and waits `Pending`; the class may be created later. The class is not read to validate a creation, because that would make creation order a rule between objects that are written independently. A growth reads it (ADR 0040 Decision 3).
3. **The `local` class.** The API server creates, at its start and when it is missing, the StorageClass `local` with `provisioner` `local` and `allowVolumeExpansion` true. `local` has the one provisioner `local` and no other class may have it: a class named `local` with another provisioner, or another class with the provisioner `local`, is `Invalid`, because `Volume.Validate` holds the rules of a local Volume by the name. An administrator who deletes `local` has the API server create it again at its next start, and one who sets `allowVolumeExpansion` to false on it has that kept, since the server creates only a missing class.
4. **Who serves a class.**
   - **`local`** is served on the Node by `storage-local`, under the Node's certificate identity as ADR 0013 and ADR 0019 have it: it makes, grows and deletes the disk of a `local` Volume pinned to its Node, and writes that Volume's `status` through the Node authorizer. Nothing in ADR 0013 or ADR 0019 changes.
   - **Any other class** is served by a cluster-side extension (goal #117 D1, D7): a process that holds its own certificate identity and an RBAC binding and that, as a client of the resource API, lists and watches StorageClasses and Volumes, serves the Volumes of the classes whose `provisioner` is its own name, readies them, writes their `status` (`phase`, `capacity`, the `Resizing` condition of ADR 0040) through `PUT /volumes/{name}/status`, and grows them. It is not an agent's plugin, needs no Node and no call in `StorageService`, and provisions a Volume when it exists, without a MicroVM that uses it. How a Node then attaches such a Volume's disk to a MicroVM is the agent's storage plugin's (ADR 0019) and is not decided here; it is an open question in [resource-api.md](../resource-api.md).
   - **How it is authorized.** Its role grants `get`, `list` and `watch` on `storageclasses` and `volumes`, and `update` on `volumes/status`. The rule language cannot limit that `update` to one class (Context), so a provisioner so bound can write the `status` of every Volume, a `local` one included, and this ADR records that as a consequence and does not close it. The `provisioner` of a class is a name the extension serves by its own choice: the API server does not check it against the caller's certificate, because nothing in the caller's identity names a class.
   - A Volume whose class does not exist, or whose class has no provisioner running, stays `Pending`, and nothing in the Volume says that no provisioner is running.
5. **Rights.** Users write StorageClasses under the rule that lets them write other kinds: `gaon:admin`'s `*`. A Node does not read them: `storage-local` knows its own class, and the API server reads the class for a growth. The controllers' role reads every kind and so reads them; `gaon:scheduler` gets no rule, since it places by Volumes and not by their class. A provisioner's role is the administrator's to bind (Decision 4).
6. **Client.** `lib/api` has `StorageClass` and `StorageClassList` with `Validate` and `ValidateUpdate`, and the constants `KindStorageClass` and `KindStorageClassList`. `StorageClassLocal` is the name and the provisioner of the built-in class.

## Consequences

- **A cluster has a list of what its storage can do.** `gaon get storageclasses` says which classes exist and whether they grow.
- **`local` is no longer special in `lib/api` alone.** It is an object, so the rule that a growth needs `allowVolumeExpansion` has one reading for it and for a third party's class.
- **An existing cluster gets the `local` class at the API server's next start**, with no step for the administrator. Until then a growth is refused for lack of a class, which is `Invalid`.
- **A third-party storage system is supplied by a process and an object**: a provisioner named `ceph`, run as a client of the resource API under a role the administrator binds, and a StorageClass with `provisioner: ceph`. Nothing is rebuilt.
- **A provisioner bound to write `volumes/status` can write every Volume's status.** The rule language has no class selector, and a label selector is judged on labels the Volume's creator sets, so it narrows nothing a creator does not choose. A mistaken or hostile provisioner can report a `local` Volume `Failed` or change its `capacity`; the `local` disk is still the Node's. Narrowing is a change to the rule language, which is not made here.
- **A provisioner that is not running is invisible in the Volume.** The Volume stays `Pending` with no condition saying why, since no process is responsible for writing one.
- **A third party's disk is not yet attachable.** The agent's storage plugin attaches a disk to a MicroVM (ADR 0019), and the contract between it and a cluster-side provisioner is open.
- **Rejected: `parameters`, `reclaimPolicy`, `mountOptions`, `volumeBindingMode` and `allowedTopologies`.** None has a reader yet. `local` takes no parameters, and a plugin has no call that would pass them. A class that needs them adds them with the plugin that does.
- **Rejected: a `StorageClass.spec`.** Kubernetes' has none, and the fields are the whole of the class, so a `spec` would add a level no one needs.
- **Rejected: leaving `local` a name with no object, and a growth refused on it by a rule in `lib/api`.** It would make the one class that exists a special case in every reader of the rule, and a user could not read from the cluster that `local` grows.
- **Rejected: validating `spec.storageClass` against the classes at creation.** It makes the creation of a Volume depend on another object being written first, and Kubernetes accepts such a claim and leaves it pending.
- **Rejected: the provisioner of every class being the Node's storage plugin, acting as its Node.** It is what an earlier draft of this ADR had. It departs from #117 D7 and D1, which make a provisioner a cluster-side extension that holds its own identity; it provisions a Volume only where a MicroVM first uses it, and a growth with no MicroVM attached waits, since no Node's plugin is given the Volume; and a shared backend has no Node to run on. The Node-side reading stays for `local`, where the disk is a file on one Node.
- **Rejected: a call in `StorageService` that tells a plugin of a Volume of its class.** A cluster-side provisioner reads Volumes through the resource API, and `local`'s plugin already reads them as its Node.
- **Rejected: the API server choosing a provisioner by class and writing it into the Volume.** The class names it, and a Volume names the class.
- **Rejected: narrowing a provisioner's rights with a class selector in the rule language.** ADR 0018's label selector is the mechanism for narrowing, and extending it to a field is a decision of its own.

## Signs the decision was wrong

- A provisioner needs a parameter of the class, such as a pool name, and has none to read.
- A provisioner bound to `volumes/status` writes a Volume of another class, and administrators ask for a rule that names a class.
- A cluster-side provisioner cannot hand a disk to the agent's storage plugin without a call this ADR does not have.
- Administrators delete `local` or turn off its expansion and are surprised that the server keeps it.
