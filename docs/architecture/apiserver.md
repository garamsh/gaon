# API server

`gaon-apiserver` serves the `v1alpha1` resource API over etcd. The contract it serves, and the invariants it holds, are in [resource-api.md](./resource-api.md); this document describes how the server is built to hold them. The module is `apiserver/`, its binary `apiserver/cmd/gaon-apiserver`.

## Current decisions

### Responsibility

The server is the only process that talks to the Store. Machines, Volumes, Nodes, Leases, CertificateSigningRequests, ClusterRoles, ClusterRoleBindings, CustomResourceDefinitions and the objects of every established definition are read and written through it by every other unit, using the client in `lib/api`. It owns the invariants the contract assigns to the API server: compare-and-swap on `resourceVersion`, the split of a resource into the sections each writer owns, the state a resource is created in, finalizers, and the check that a Lease names an existing Node. Every rule that is a pure function of resources (`Validate`, `Bind`, `ValidateStatusUpdate`, `Attach`, `ValidateStatus`) lives in `lib/api` and the server calls it; the server adds only what needs the Store.

### Shape

The module follows the service layout of the stack convention. A transport at the module root decodes a request, calls one service method and translates its error; the service holds the rules; a Store interface is the only way the service reaches etcd, and one implementation of it wraps the etcd client.

- The transport serves every path of resource-api.md §Paths under the root `/apis/compute.gaon.garam.sh/v1alpha1` on the server's address, the paths of ClusterRoles and ClusterRoleBindings under the root `/apis/rbac.gaon.garam.sh/v1alpha1`, the paths of CustomResourceDefinitions under the root `/apis/apiextensions.gaon.garam.sh/v1alpha1`, the paths of the two webhook-configuration kinds under the root `/apis/admissionregistration.gaon.garam.sh/v1alpha1`, and the paths of a registered kind under `/apis/<group>/<version>/<plural>`, and answers any other path, or one that no definition serves, with the `NotFound` error object. Each route names the API group, the resource and the verb it is, and asks an authorizer before its handler runs. It has one error translator: an `APIError` becomes its code and body, and any other error is logged once and answered as `Internal`, 500.
- The service has one generic description of a kind (its path prefix and how its resources are keyed) and one file of rules per kind. A kind that needs no rule beyond the generic ones adds none.
- The authorizers are a package of their own, `internal/authorization`, which reads the resources it decides on through an interface the service satisfies. It holds the Node authorizer, the RBAC authorizer, the escalation check and the bootstrap policy.
- The Store interface speaks in keys, bytes and revisions: get, list, create, update at a revision, delete, watch from a revision, and one transaction over several keys. It knows nothing of resources.

### The Store

`resourceVersion` is the etcd mod revision of the key, as the contract fixes. A resource is stored as its JSON without the version, under `/registry/<plural>/<name>`; the version is set on every read from the revision.

- A create is a transaction that succeeds only where the key does not exist; an update and a delete are transactions that succeed only where the key's mod revision equals the one the service read. A transaction that fails reads the key again to say whether it was missing or stale. Two writers of one version cannot both win, which is the property the contract builds on.
- A transaction over several keys writes each value only if every key's mod revision is still the one the service read, and a key given no value is checked and not written. It succeeds whole or not at all, and a failed condition is `Conflict`. The binding of a Machine uses it.
- The service reads before it writes, so it can check the version, run the rules and refuse early; the transaction is the guard that holds under a race.
- A list is one read, and its response carries the revision the read was made at. Listing, then watching from that version, loses nothing and replays nothing.
- A watch is an etcd watch from the given version plus one, on the kind's prefix. A `Deleted` event carries the last stored value, with its version set to the revision of the deletion.
- A compacted version ends the stream with an `Error` event whose reason is `Expired`, as the contract fixes; it is the last event, and the HTTP response is a stream, not an error status. A watch without a version, or with one that is not a number, is refused with `Invalid` before the stream opens.

### Writes

Every write to an existing resource carries the version it was read at, and a write without it or with a stale one gets `Conflict`; a write to a resource that does not exist gets `NotFound`. A PUT without a version creates and gets `AlreadyExists` where the name is taken.

- **Sections.** A spec PUT keeps the stored status, binding fields and deletion timestamp; a status PUT keeps the stored spec and metadata; the binding path sets only `spec.nodeName` and `spec.bindingEpoch`. The contract names a writer for each section, and the server cannot tell writers apart, because authentication gives it an identity but no rule on which identity writes which section (see open questions); it keeps the sections apart by the path a write arrives on.
- **Generation.** The generation of a resource is 1 on creation and grows by one on every write that changes its spec, a binding included.
- **Creation.** A Machine is created `Pending`, with no node and no epoch; a create that carries a node or an epoch is `Invalid`. A Node is created `Discovered`, whatever status the body carries.
- **Node state.** A Node status write that changes `status.state` must set the state that agrees with the stored `spec.admitted`: `Admitted` where it is true, `Discovered` where it is false. A write that leaves the state as stored is accepted whatever `spec.admitted` is, so one writer's lag, such as the node lifecycle controller writing `LeaseExpired` while the Node Agent has not yet moved the state, does not block another writer's section. The server does not move the state when the spec changes; the Node Agent does, through a status write.
- **Lease.** A Lease is named as the Node it belongs to; a write for a name that is no Node is `Invalid`.
- **Volume.** A Volume status write that changes the attachment must name a Machine that exists, at that Machine's current binding epoch, and then holds only where `Volume.Attach` accepts it: the Volume is unattached or attached at a lower epoch. The first failure is `Invalid`, the second `Conflict`. A status write for an absent Volume is `NotFound`.
- **Volume creation and update.** A Volume is served at `PUT`, `GET`, `DELETE` `/volumes/{name}`, `GET /volumes` and `GET /volumes?watch=true`, with the rules above. A create is `Pending` whatever `status` the body carries, with generation 1; a create that carries `spec.nodeName` is `Invalid`, because only a binding pins a Volume. An update runs `Volume.ValidateUpdate` against the stored Volume, so a spec change is `Invalid`; it keeps the stored status and deletion timestamp, and a change to the finalizer entries alone is accepted.
- **Volume pin at the binding.** The binding of a Machine pins each unpinned `local` Volume the Machine names to the Node and adds the finalizer `compute.gaon.garam.sh/node-agent`, with `Machine.PinVolumes`, in the same transaction as the Machine. The Machine and every Volume it uses are read first; the transaction is conditioned on the version of each as read, and a Volume that is unchanged by the pin is checked and not written. A Volume pinned to another Node or being deleted is `Conflict`, a Volume that does not exist is `Invalid`, a Volume of another class is left as it is, and nothing is written on a refusal. A Volume changed after the binding read it makes the transaction `Conflict`, so of two bindings that race for one Volume exactly one pins it. The Volumes written share the Machine's `resourceVersion`.
- **Finalizers.** A delete of a resource with finalizers sets its deletion timestamp and keeps it; a second delete keeps the first timestamp. A finalizer cannot be added once the timestamp is set. The write that clears the last finalizer of a resource being deleted removes it, and the watch shows `Deleted`. A resource without finalizers is removed by the delete at once. The deletion timestamp comes from the server's clock, injected so a test can fix it.
- **Bodies.** A body is refused if it has a field the type does not, if anything follows the value, or if it is over 1 MiB. A body whose name differs from the path, or a name with a slash, is `Invalid`; a slash would address another key.

### Custom resources

The server serves a CustomResourceDefinition and the objects of each established definition ([ADR 0009](./adr/0009-a-user-registers-a-resource-kind-with-a-customresourcedefinition-the-api-server-serves-it-under-its-own-group.md), resource-api.md §CustomResourceDefinition).

- **Definitions.** A definition is validated by `lib/api` and stored under `/registry/customresourcedefinitions/<name>`. The server writes its status: `NamesAccepted` and `Established`. A body's status is never taken. A definition's group, names and version name cannot change, and its schema and subresources can.
- **Names.** `NamesAccepted` is false where an older definition of the same group, one that holds its names, has the same `kind`, `listKind`, `plural` or `singular`. The older keeps its names, and a definition that is not accepted holds none. A definition that is not accepted serves no path.
- **Paths.** A path is served while its definition's names are accepted and the version matches. A kind is stored under its definition's name, which holds a dot where no core plural does, so a custom kind cannot collide with a core one.
- **Objects.** The schema prunes every field it does not name, except under a node that preserves unknown fields, and refuses a value that fails its type, `enum`, `minimum`, `maximum`, `pattern`, `required` or `items` as `Invalid`. A `null` on a named property is an absent one. Generation, finalizers, deletion and compare-and-swap are the Machine's.
- **Status.** Where the definition enables the status subresource, an object's PUT ignores `status` and a create drops it, and a PUT to `/status` writes `status` only; the path is `NotFound` otherwise. Without the subresource the PUT writes the status, as it does the spec.
- **Deleting a definition.** The server sets the deletion timestamp and `Established` false; deletes each object as a user's delete would; and removes the definition once none is left. A terminating definition refuses a create with `Conflict` and serves every other path. An object held by a finalizer keeps the definition until its finalizer is cleared. The streams of the kind's objects end when the definition is removed, after their last event. A repeated delete of a terminating definition does not check the version, so a delete cut short can be repeated.
- **Races.** A definition write takes a lock that an object write shares, so a create cannot land after the definition's removal.
- **Authorization.** A request to a definition path is the group `apiextensions.gaon.garam.sh` and the resource `customresourcedefinitions`; a request to an object path is the definition's group and its plural, or `<plural>/status`. A bearer-token holder reaches none of them.

### Admission webhooks

The server stores MutatingWebhookConfigurations and ValidatingWebhookConfigurations and calls the webhooks they register on a write ([ADR 0010](./adr/0010-a-user-registers-admission-webhooks-with-webhook-configurations-the-api-server-calls-them-on-every-accepted-write.md), resource-api.md §Admission webhooks). The package `internal/admission` holds the matching, the call and the patch; the service calls it from each write.

- **Configurations.** The two kinds are served under `/apis/admissionregistration.gaon.garam.sh/v1alpha1`, validated by `lib/api` and stored like any kind. A request to them is the group `admissionregistration.gaon.garam.sh` and the resource `mutatingwebhookconfigurations` or `validatingwebhookconfigurations`. A write to either kind is never sent to a webhook, so a configuration can always be repaired, and a read is never sent.
- **Order.** A write runs the mutating webhooks, then the server's own validation, then the validating webhooks, then the Store. The configurations are read from the Store at each write, so an edit takes effect on the next one. Mutating configurations are called in the order of their names, and the webhooks of one in its listed order; each sees the object as the one before left it. Validating webhooks see the object the server would store.
- **A call.** A webhook whose rules match the operation, group, version and resource, with its subresource, is sent a POST of an AdmissionReview with a fresh `uid`, as `application/json`, over TLS that trusts its `caBundle` and nothing else, with no redirect followed. `userInfo` is the identity the transport authenticated, as the authorizers see it; plain HTTP has none. The call is bounded by the webhook's timeout. The answer must be status 200, a body of at most 16 MiB that decodes, and the same `uid`.
- **An answer.** `allowed: false` is `Forbidden`, 403, naming the webhook and its configuration and carrying `status.message`, whatever `status.code` says and whatever the failure policy is. A patch is JSON Patch; it is applied to the object as sent, and a patch that does not apply, that is malformed, or that changes `apiVersion`, `kind`, `metadata.name` or `metadata.resourceVersion` is a failed call, with none of it applied. A validating webhook that answers with a patch, and any webhook that answers a delete with one, has failed.
- **A failed call** is `InternalError`, 500, under `Fail`, and the webhook is skipped under `Ignore`, its patch included. A timeout, an untrusted certificate, a status other than 200, an undecodable body, a wrong `uid` and a bad patch each count.
- **Which writes.** Every write of a resource through the API that changes the Store as a user's would: a create, an update, a status write, a delete and the binding of a Machine, which is sent as a CREATE of a `Binding` on `machines/binding` and, for each Volume it pins, as an UPDATE of the Volume, with both stages, before the transaction. A delete is sent with `oldObject` and no `object`. A delete of an object that is already being deleted changes nothing and is not sent. The deletes a definition's removal makes of its objects are sent each as a user's delete, and run under the definition lock, so their timeouts bound how long that lock is held. A write the server makes for itself, such as the bootstrap policy, is not sent.
- **A mutated update.** A mutating webhook that changes an update is held to the same rules as the caller: a change to a field the write may not touch is `Invalid` after the patch, not accepted.
- **Custom resources.** An object of a custom kind is sent with its definition's group, version, kind and plural.

### Running

`Run` takes a listener, a configuration and a context, and serves until the context ends, then stops accepting and drains for a short time. Without the TLS files the server serves plain HTTP and `Run` refuses a listener that is not on a loopback address. With them it serves TLS on any address, loopback included: the server speaks TLS 1.3 or later and verifies a client certificate, against the client CA, when one is given without requiring one ([ADR 0005](./adr/0005-the-api-server-serves-beyond-loopback-only-with-mutual-tls.md), narrowed by [ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md)). The binary reads the etcd endpoints, the listen address, the dial timeout, the TLS files and the bootstrap token file from flags and defaults to loopback for the listener.

- `--tls-client-ca`, `--tls-cert` and `--tls-key` are the PEM files of the client CA and of the server's certificate and key. All three are given or none is, and a partial set, or a file that does not load, stops the server at start.
- The certificate's subject CN is the caller's user, a Node Agent's being its Node name, and the Organization values of its subject are its groups. What the server does with them depends on `--authorization-mode`.
- **Callers, told apart before a request is routed** ([ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md)):
  - A request with a verified certificate is served as every request was under ADR 0005.
  - A request with no certificate and a valid bearer token has the identity `bootstrap:<id>` and may reach only the create and the read of one CertificateSigningRequest. Any other route is `Forbidden`, and so is reading a request whose `spec.username` is another identity. Routes are allowed to a token one by one: a route added later is closed to it.
  - A request with no certificate and a missing or invalid token is `Unauthorized`. The server compares the token's secret in constant time.
  - Plain HTTP authenticates nobody and honours no token, so a request created there has an empty `spec.username`, which the signer's rule denies.
- **`--authorization-mode`** is `AlwaysAllow`, the default, or `RBAC` ([ADR 0008](./adr/0008-the-api-server-authorizes-certificate-callers-with-cluster-roles-bindings-and-a-node-authorizer.md)); any other value, including one in another case, stops the server at start. `RBAC` without the three TLS files stops it at start too, because a request without a client certificate has no identity to authorize.
  - **`AlwaysAllow`** serves every request as ADR 0005 did. ClusterRoles and ClusterRoleBindings can be written and read, and decide nothing; the server creates none.
  - **`RBAC`** authorizes every request made with a certificate. The order is fixed: the Node authorizer first, then the ClusterRoles bound to the caller's user or to one of its groups. The Node authorizer never refuses; a request it does not allow goes to RBAC, and a request neither allows is `Forbidden`, 403. A Node may read Volumes, write the `status` of a Volume pinned to it or used by a Machine bound to it, and `PUT` a Volume pinned to it only where the body differs from the stored Volume in the node-agent finalizer alone; it creates and deletes none. The Volume rule is the Machine's, and a role that grants `update` on `volumes` is not held to it. A `PUT /machines/{name}` update from a caller whose only grant is the Node authorizer's is `Forbidden` unless the body differs from the stored Machine in `metadata.finalizers` alone, and there only by adding or removing `compute.gaon.garam.sh/node-agent` (the contract's invariant 3); the status and the fields the server sets are not compared, and a caller with `update` on `machines` from a role is not held to this. A request is its verb, its API group and its resource with the subresource, as ADR 0008 Decision 4 describes it: a `PUT` is `create` where its body carries no `resourceVersion` and `update` where it does, a read of a collection is `list`, or `watch` with `watch=true`. The server reads the roles and bindings from the Store for every request, so an edit takes effect on the next one.
  - **A bearer-token holder** is not authorized by either: the routes of ADR 0007 are the whole of what it may do, and no role widens or narrows them.
  - **The escalation rule** is checked before a ClusterRole or a ClusterRoleBinding is written. A role is refused as `Forbidden` unless the caller holds every permission its rules grant, a binding unless the caller holds every permission of the role it references, and `*` is held only by a rule that has `*`. A binding whose `roleRef` names no ClusterRole is `Invalid`. A delete needs only `delete`, and the permissions the Node authorizer gives a caller are not counted as held. A refused write stores nothing.
  - **The bootstrap policy** is created at start in `RBAC` mode: the ClusterRoles `gaon:scheduler` (which reads `machines`, `nodes` and `volumes`), `gaon:controllers` and `gaon:admin`, and a binding of each to the group `gaon:schedulers`, `gaon:controllers` and `gaon:admins`. An object that exists is never overwritten, so an operator's edit survives a restart, and one that is missing is created again.
- **`--bootstrap-token-file`** is a file of valid tokens, one per line, read once at start; blank lines are ignored and removing a token takes effect at the next start. A line that is not a token, a file that cannot be read, and the flag without the three TLS files stop the server at start.
- **CertificateSigningRequest.** A create sets `spec.username` from the caller's identity and drops any status it carries. A `PUT` that carries `metadata.resourceVersion` is `Invalid`, because the spec is immutable. The status path stores the conditions and the certificate under `ValidateStatus`, by compare-and-swap. List and watch are not open to a token holder.
- The server reads the files once at start. It dials etcd at start and fails if it cannot.

## Rationale

- Mutual TLS beyond loopback, the certificate's CN as identity, and authentication without authorization: [ADR 0005](./adr/0005-the-api-server-serves-beyond-loopback-only-with-mutual-tls.md). The authorization modes, the Node authorizer ahead of RBAC, the bootstrap roles and the escalation rule: [ADR 0008](./adr/0008-the-api-server-authorizes-certificate-callers-with-cluster-roles-bindings-and-a-node-authorizer.md). The bootstrap token and the narrowed listener: [ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md).
- The Store is etcd, and `resourceVersion`, compare-and-swap and watch map onto etcd's revisions, transactions and watches: [ADR 0004](./adr/0004-the-store-is-etcd-in-one-cell-of-one-member.md). Keeping the Store behind an interface of keys and revisions keeps the rules testable against a real etcd without the rules knowing it.
- One writer per section, and the Lease and the epoch as the fence against a stale writer: [ADR 0003](./adr/0003-the-v1alpha1-resource-api-fixes-one-writer-per-section-and-a-per-node-lease.md). The server holds the invariants the contract gives it; it does not duplicate the rules that `lib/api` owns, so a client and the server cannot disagree about them.
- A user-registered kind is served from the definition read at each request, so a definition's change takes effect on the next one: [ADR 0009](./adr/0009-a-user-registers-a-resource-kind-with-a-customresourcedefinition-the-api-server-serves-it-under-its-own-group.md).
- Webhooks are called from each write in the service, not from a Store decorator, which could not tell a user's operation from one the server makes for itself, and not from the transport, which cannot run the server's own validation between the two stages: [ADR 0010](./adr/0010-a-user-registers-admission-webhooks-with-webhook-configurations-the-api-server-calls-them-on-every-accepted-write.md).
- The server is its own module with its own binary, a unit of the workspace: [ADR 0001](./adr/0001-the-repository-is-a-go-workspace-of-executable-units-partitioned-by-responsibility.md). It imports `lib/api` and nothing else of gaon.
- Tests run the server over an embedded etcd member started in the test process, because no etcd binary is assumed on a developer machine or a CI runner. The etcd server module is a dependency of the tests only; the binary links the etcd client alone. The module is on `go 1.26.0`, as is the workspace, and pins etcd 3.6.16, the newest 3.6 release, with `golang.org/x/net` 0.62.0 and `google.golang.org/grpc` 1.83.2 that it requires. Release 3.6.4, the first pin, carried a client that reached vulnerable code in x/net and grpc from the shipped binary, and the releases that fix them need Go 1.25 or later, which is why the workspace's Go version moved. `govulncheck` over the module reports nothing under Go 1.26.11 and reports only standard library findings under 1.26.0, so the workspace's `toolchain` directive in `go.work` names a 1.26 patch release, which CI and a developer's `go` command build with, and the owner of `go.work` moves it by hand. The pin moves with the Dependabot entry for the module, and with the workspace's Go version.

## Open questions

- **A delete cut short.** A crash after a definition is marked terminating, and before its objects are gone, leaves it terminating and its objects deleting; nothing finishes it until the delete is repeated or an object's last finalizer is cleared.
- **Finalizers on a definition.** The server sets the deletion timestamp of a definition and does not honour a finalizer on it.
- **Authorization by field beyond the Machine and Volume finalizer.** In `RBAC` mode the server checks the path an identity may write, and for `PUT /machines/{name}` and `PUT /volumes/{name}` the part of the body it changes; no other write is checked by field. In `AlwaysAllow`, the default, any authenticated caller may write any path.
- **Node created with `spec.admitted` true.** The server starts every Node `Discovered`, so one created already admitted waits for the Node Agent to move its state. The contract does not say whether a create may carry `admitted`.
- **The `Deleted` event.** It carries the last stored value, not the resource as the delete left it, so a consumer sees the finalizer-free state only through the preceding `Modified`. The contract does not say which a consumer should expect.
- **Compaction.** Nothing compacts etcd yet. A watch expires only when an operator compacts, and a cell that is never compacted grows without bound.
- **More than one member.** The server dials the endpoints it is given and relies on etcd's linearizable reads; it has not been run against a cell of more than one member.
