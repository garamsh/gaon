# API server

`gaon-apiserver` serves the `v1alpha1` resource API over etcd. The contract it serves, and the invariants it holds, are in [resource-api.md](./resource-api.md); this document describes how the server is built to hold them. The module is `apiserver/`, its binary `apiserver/cmd/gaon-apiserver`.

## Current decisions

### Responsibility

The server is the only process that talks to the Store. MicroVMs, Volumes, Nodes, Leases, Events, Secrets, ConfigMaps, ServiceAccounts, the coordination group's Leases, CertificateSigningRequests, ClusterRoles, ClusterRoleBindings, CustomResourceDefinitions and the objects of every established definition are read and written through it by every other unit, using the client in `lib/api`. It owns the invariants the contract assigns to the API server: compare-and-swap on `resourceVersion`, the split of a resource into the sections each writer owns, the state a resource is created in, finalizers, and the check that a Lease names an existing Node. Every rule that is a pure function of resources (`Validate`, `Bind`, `ValidateStatusUpdate`, `Attach`, `ValidateStatus`) lives in `lib/api` and the server calls it; the server adds only what needs the Store.

### Shape

The module follows the service layout of the stack convention. A transport at the module root decodes a request, calls one service method and translates its error; the service holds the rules; a Store interface is the only way the service reaches etcd, and one implementation of it wraps the etcd client.

- The transport serves every path of resource-api.md §Paths under the root `/apis/compute.gaon.garam.sh/v1alpha1` on the server's address, the paths of ClusterRoles and ClusterRoleBindings under the root `/apis/rbac.gaon.garam.sh/v1alpha1`, the paths of CustomResourceDefinitions under the root `/apis/apiextensions.gaon.garam.sh/v1alpha1`, the paths of the two webhook-configuration kinds under the root `/apis/admissionregistration.gaon.garam.sh/v1alpha1`, the paths of the coordination group's Lease under the root `/apis/coordination.gaon.garam.sh/v1alpha1`, and the paths of a registered kind under `/apis/<group>/<version>/<plural>`, and answers any other path, or one that no definition serves, with the `NotFound` error object. Each route names the API group, the resource and the verb it is, and asks an authorizer before its handler runs. It has one error translator: an `APIError` becomes its code and body, and any other error is logged once and answered as `Internal`, 500.
- The transport also serves Secrets, ConfigMaps and ServiceAccounts under the compute root, each with put, delete, get, list and watch, and `POST /serviceaccounts/{name}/token` ([ADR 0020](./adr/0020-a-microvm-takes-a-process-ports-files-and-probes-secret-configmap-and-serviceaccount-are-kinds-and-a-token-request-returns-a-jwt-bound-to-a-microvm.md)). A write of each is checked with the kind's `Validate` and goes through the webhook flow like any other kind's. A Secret's data is never written to a log line or an error, because the server logs a Secret by name only.
- **The token request** is a `POST` that is not stored and is not sent to any admission webhook. The service reads the ServiceAccount and the bound MicroVM, calls `api.NewTokenClaims` (which refuses a MicroVM of another uid or name, one being deleted and another service account, and bounds the lifetime), and signs the claims as a JWT with ES256 under the configured key. The route's resource is `serviceaccounts/token`, verb `create`. With no signing key configured the route answers `Internal`, 500.
- The service has one generic description of a kind (its path prefix and how its resources are keyed) and one file of rules per kind. A kind that needs no rule beyond the generic ones adds none.
- The authorizers are a package of their own, `internal/authorization`, which reads the resources it decides on through an interface the service satisfies. It holds the Node authorizer, the RBAC authorizer, the escalation check and the bootstrap policy.
- The Store interface speaks in keys, bytes and revisions: get, list, create, update at a revision, delete, watch from a revision, and one transaction over several keys. It knows nothing of resources.

### The Store

`resourceVersion` is the etcd mod revision of the key, as the contract fixes. A resource is stored as its JSON without the version, under `/registry/<plural>/<name>`; the version is set on every read from the revision.

- A create is a transaction that succeeds only where the key does not exist; an update and a delete are transactions that succeed only where the key's mod revision equals the one the service read. A transaction that fails reads the key again to say whether it was missing or stale. Two writers of one version cannot both win, which is the property the contract builds on.
- A transaction over several keys writes each value only if every key's mod revision is still the one the service read, and a key given no value is checked and not written. It succeeds whole or not at all, and a failed condition is `Conflict`. The binding of a MicroVM uses it.
- The service reads before it writes, so it can check the version, run the rules and refuse early; the transaction is the guard that holds under a race.
- A list is one read, and its response carries the revision the read was made at. Listing, then watching from that version, loses nothing and replays nothing.
- A watch is an etcd watch from the given version plus one, on the kind's prefix. A `Deleted` event carries the last stored value, with its version set to the revision of the deletion. The Store's event for a change carries the value it replaced, so a watch with a label selector can tell an object that starts to match from one that stops.
- A list or a watch with a `labelSelector` ([ADR 0018](./adr/0018-metadata-gains-uid-labels-and-owner-references-lists-take-a-label-selector-lease-and-event-are-new-kinds-and-a-role-rule-may-carry-a-label-selector.md)) reads the kind's prefix whole and sends the objects the selector selects. A watch compares the labels before and after each change: `Added` when the object starts to match, `Deleted` when it stops matching, `Modified` when it matches both times, and nothing when it matches neither. A `Modified` change whose previous value the Store has compacted ends the stream with `Expired`. A selector that does not parse is `Invalid`, before a stream opens.
- A compacted version ends the stream with an `Error` event whose reason is `Expired`, as the contract fixes; it is the last event, and the HTTP response is a stream, not an error status. A watch without a version, or with one that is not a number, is refused with `Invalid` before the stream opens.

### Writes

Every write to an existing resource carries the version it was read at, and a write without it or with a stale one gets `Conflict`; a write to a resource that does not exist gets `NotFound`. A PUT without a version creates and gets `AlreadyExists` where the name is taken.

- **Sections.** A spec PUT keeps the stored status, binding fields and deletion timestamp; a status PUT keeps the stored spec and metadata; the binding path sets only `spec.nodeName` and `spec.bindingEpoch`. The contract names a writer for each section, and the server cannot tell writers apart, because authentication gives it an identity but no rule on which identity writes which section (see open questions); it keeps the sections apart by the path a write arrives on.
- **Generation.** The generation of a resource is 1 on creation and grows by one on every write that changes its spec, a binding included.
- **Creation.** A MicroVM is created `Pending`, with no node and no epoch; a create that carries a node or an epoch is `Invalid`. A Node is created `Discovered`, whatever status the body carries.
- **Node state.** A Node status write that changes `status.state` must set the state that agrees with the stored `spec.admitted`: `Admitted` where it is true, `Discovered` where it is false. A write that leaves the state as stored is accepted whatever `spec.admitted` is, so one writer's lag, such as the node lifecycle controller writing `LeaseExpired` while the Node Agent has not yet moved the state, does not block another writer's section. The server does not move the state when the spec changes; the Node Agent does, through a status write.
- **Lease.** A Lease is named as the Node it belongs to; a write for a name that is no Node is `Invalid`.
- **Coordination Lease and Event.** Each is created and updated by compare-and-swap like any kind, runs the validation of `lib/api`, and goes through the admission webhooks. A coordination Lease is named freely and needs no Node. It is stored under `/registry/leases.coordination.gaon.garam.sh/<name>`, so it never meets the Node's Lease at `/registry/leases/<name>`, and a webhook sees it as the resource `leases` of its own group. An Event update may raise `count` and move `lastTimestamp` and change nothing else of its object, reason or type.
- **Metadata.** Every write of every kind runs `ObjectMeta.Validate`, and a create runs `ValidateCreate` and an update `ValidateUpdate` against the stored metadata; a failure is `Invalid`. The server sets `metadata.uid` at create and replaces one the request carries. An update keeps the stored uid, so one that carries another is `Invalid` and one that carries none keeps the stored value. An object stored without a uid takes one on its next write. A status write and a delete carry no metadata of their own and keep the stored one.
- **Volume.** A Volume status write that changes the attachment must name a MicroVM that exists, at that MicroVM's current binding epoch, and then holds only where `Volume.Attach` accepts it: the Volume is unattached or attached at a lower epoch. The first failure is `Invalid`, the second `Conflict`. A status write for an absent Volume is `NotFound`.
- **Volume creation and update.** A Volume is served at `PUT`, `GET`, `DELETE` `/volumes/{name}`, `GET /volumes` and `GET /volumes?watch=true`, with the rules above. A create is `Pending` whatever `status` the body carries, with generation 1; a create that carries `spec.nodeName` is `Invalid`, because only a binding pins a Volume. An update runs `Volume.ValidateResize` against the stored Volume and the StorageClass that `spec.storageClass` names, read from the Store just before the write and not in its transaction. A change of any other field of `spec` is `Invalid`, as is a `storage` below `status.capacity` and a growth under no class or a class that forbids expansion; a growth of a Volume being deleted is `Conflict`. The generation advances only where `spec` changes, so the same size in another unit is no new generation. The update keeps the stored status and deletion timestamp, and a change to the finalizer entries alone is accepted. A status write takes `status.conditions` as `Volume.ValidateStatus` checks them.
- **StorageClass.** A StorageClass is served cluster-scoped at `PUT`, `GET`, `DELETE` `/storageclasses/{name}`, `GET /storageclasses` and `GET /storageclasses?watch=true`, checked by `StorageClass.Validate` on a write and `ValidateUpdate` on an update, so a provisioner cannot change. At start, in every authorization mode, the server creates the class `local` (provisioner `local`, `allowVolumeExpansion` true) through the same write as a user's, and leaves one that exists as it is, changed or not. The Node authorizer grants a Node nothing on `storageclasses`, so RBAC decides: the controllers role reads it through its `*` read, the scheduler role has no rule for it, and admin has `*`.
- **Volume pin at the binding.** The binding of a MicroVM pins each unpinned `local` Volume the MicroVM names to the Node and adds the finalizer `compute.gaon.garam.sh/node-agent`, with `MicroVM.PinVolumes`, in the same transaction as the MicroVM. The MicroVM and every Volume it uses are read first; the transaction is conditioned on the version of each as read, and a Volume that is unchanged by the pin is checked and not written. A Volume pinned to another Node or being deleted is `Conflict`, a Volume that does not exist is `Invalid`, a Volume of another class is left as it is, and nothing is written on a refusal. A Volume changed after the binding read it makes the transaction `Conflict`, so of two bindings that race for one Volume exactly one pins it. The Volumes written share the MicroVM's `resourceVersion`.
- **Service, Endpoints and NetworkPolicy.** Each is served at `PUT`, `GET`, `DELETE` `/<plural>/{name}`, `GET /<plural>` and `GET /<plural>?watch=true`, with the rules above, runs `Validate` before the write and the admission webhooks, and takes a `labelSelector`. An update to a Service calls `KeepAllocated` with the stored Service before it is validated, so an empty `clusterIP` keeps the address and the update does not count as a change, then `ValidateUpdate`; it keeps the stored `status`. A delete of any of the three removes it at once: no finalizer is honoured, as for Secret.
- **Allocation of a Service's addresses** (resource-api.md §Service, Endpoints and NetworkPolicy, [ADR 0027](./adr/0027-a-service-allocates-its-addresses-from-two-configured-ranges-endpoints-lists-its-ready-microvms-and-a-networkpolicy-selects-microvms-by-label.md)).
  - A create reads the keys under `/allocations/service-ip/` and, for a `LoadBalancer`, `/allocations/lan/`, and chooses each address: the one the Service asks for in `spec.clusterIP` or `spec.loadBalancerIP`, else a free one, found from a random start of the range and going up. It writes the cluster address into `spec.clusterIP` and the LAN address into `status.loadBalancer.ingress`, and stores the Service and a key for each address, whose value is the Service's name, in one transaction that requires every key to be absent.
  - A key that another API server took between the read and the write fails the transaction; the server reads again and chooses again, at most 5 times (`fenceAttempts`), then answers `Conflict`.
  - A requested address outside its range, or equal to the network or broadcast address of an IPv4 range of four or more addresses, is `Invalid`. An address held by another Service, and a range with no free address, are `Conflict`. A name that is taken is `AlreadyExists`, checked before any address.
  - A delete removes the Service and, in the same transaction, the keys of its addresses whose value is its name. A key another Service holds is left as it is.
  - A server started without `--service-cluster-ip-range` answers a create that needs a cluster address with 500, and without `--load-balancer-pool` a `LoadBalancer` create the same; a headless `ClusterIP` Service needs neither.
- **Finalizers.** A delete of a resource with finalizers sets its deletion timestamp and keeps it; a second delete keeps the first timestamp. A finalizer cannot be added once the timestamp is set. The write that clears the last finalizer of a resource being deleted removes it, and the watch shows `Deleted`. A resource without finalizers is removed by the delete at once. The deletion timestamp comes from the server's clock, injected so a test can fix it.
- **Bodies.** A body is refused if it has a field the type does not, if anything follows the value, or if it is over 1 MiB. A body whose name differs from the path, or a name with a slash, is `Invalid`; a slash would address another key.

### Custom resources

The server serves a CustomResourceDefinition and the objects of each established definition ([ADR 0009](./adr/0009-a-user-registers-a-resource-kind-with-a-customresourcedefinition-the-api-server-serves-it-under-its-own-group.md), resource-api.md §CustomResourceDefinition).

- **Definitions.** A definition is validated by `lib/api` and stored under `/registry/customresourcedefinitions/<name>`. The server writes its status: `NamesAccepted` and `Established`. A body's status is never taken. A definition's group, names and version name cannot change, and its schema and subresources can.
- **Names.** `NamesAccepted` is false where an older definition of the same group, one that holds its names, has the same `kind`, `listKind`, `plural` or `singular`. The older keeps its names, and a definition that is not accepted holds none. A definition that is not accepted serves no path.
- **Paths.** A path is served while its definition's names are accepted and the version matches. A kind is stored under its definition's name, which holds a dot where no core plural does, so a custom kind cannot collide with a core one.
- **Objects.** The schema prunes every field it does not name, except under a node that preserves unknown fields, and refuses a value that fails its type, `enum`, `minimum`, `maximum`, `pattern`, `required` or `items` as `Invalid`. A `null` on a named property is an absent one. Generation, finalizers, deletion and compare-and-swap are the MicroVM's.
- **Status.** Where the definition enables the status subresource, an object's PUT ignores `status` and a create drops it, and a PUT to `/status` writes `status` only; the path is `NotFound` otherwise. Without the subresource the PUT writes the status, as it does the spec.
- **Deleting a definition.** The server sets the deletion timestamp and `Established` false; deletes each object as a user's delete would; and removes the definition once none is left. A terminating definition refuses a create with `Conflict` and serves every other path. An object held by a finalizer keeps the definition until its finalizer is cleared. The streams of the kind's objects end when the definition is removed, after their last event. A repeated delete of a terminating definition does not check the version, so a delete cut short can be repeated.
- **Races.** An object's create is one etcd transaction that also compares the definition's key at the revision read, so a create cannot land once the definition is changed or marked deleted, and the removal after an empty list leaves no object. A definition's create also compares the key `/locks/customresourcedefinition-names` at the revision read before the others were listed, so of creates that share a name one stores and the others read again. Both hold across API server processes, because etcd orders them and no process holds a lock; the loser of either retries up to five times, then `Conflict`. [ADR 0023](./adr/0023-the-control-plane-runs-on-three-nodes-over-a-three-member-etcd-and-the-scheduler-and-the-controllers-act-only-while-holding-a-coordination-lease.md).
- **Authorization.** A request to a definition path is the group `apiextensions.gaon.garam.sh` and the resource `customresourcedefinitions`; a request to an object path is the definition's group and its plural, or `<plural>/status`. A bearer-token holder reaches none of them.

### Admission webhooks

The server stores MutatingWebhookConfigurations and ValidatingWebhookConfigurations and calls the webhooks they register on a write ([ADR 0010](./adr/0010-a-user-registers-admission-webhooks-with-webhook-configurations-the-api-server-calls-them-on-every-accepted-write.md), resource-api.md §Admission webhooks). The package `internal/admission` holds the matching, the call and the patch; the service calls it from each write.

- **Configurations.** The two kinds are served under `/apis/admissionregistration.gaon.garam.sh/v1alpha1`, validated by `lib/api` and stored like any kind. A request to them is the group `admissionregistration.gaon.garam.sh` and the resource `mutatingwebhookconfigurations` or `validatingwebhookconfigurations`. A write to either kind is never sent to a webhook, so a configuration can always be repaired, and a read is never sent.
- **Order.** A write runs the mutating webhooks, then the server's own validation, then the validating webhooks, then the Store. The configurations are read from the Store at each write, so an edit takes effect on the next one. Mutating configurations are called in the order of their names, and the webhooks of one in its listed order; each sees the object as the one before left it. Validating webhooks see the object the server would store.
- **A call.** A webhook whose rules match the operation, group, version and resource, with its subresource, is sent a POST of an AdmissionReview with a fresh `uid`, as `application/json`, over TLS that trusts its `caBundle` and nothing else, with no redirect followed. `userInfo` is the identity the transport authenticated, as the authorizers see it; plain HTTP has none. The call is bounded by the webhook's timeout. The answer must be status 200, a body of at most 16 MiB that decodes, and the same `uid`.
- **An answer.** `allowed: false` is `Forbidden`, 403, naming the webhook and its configuration and carrying `status.message`, whatever `status.code` says and whatever the failure policy is. A patch is JSON Patch; it is applied to the object as sent, and a patch that does not apply, that is malformed, or that changes `apiVersion`, `kind`, `metadata.name` or `metadata.resourceVersion` is a failed call, with none of it applied. A validating webhook that answers with a patch, and any webhook that answers a delete with one, has failed.
- **A failed call** is `InternalError`, 500, under `Fail`, and the webhook is skipped under `Ignore`, its patch included. A timeout, an untrusted certificate, a status other than 200, an undecodable body, a wrong `uid` and a bad patch each count.
- **Which writes.** Every write of a resource through the API that changes the Store as a user's would: a create, an update, a status write, a delete and the binding of a MicroVM, which is sent as a CREATE of a `Binding` on `microvms/binding` and, for each Volume it pins, as an UPDATE of the Volume, with both stages, before the transaction. A delete is sent with `oldObject` and no `object`. A delete of an object that is already being deleted changes nothing and is not sent. The deletes a definition's removal makes of its objects are sent each as a user's delete, and run under the definition lock, so their timeouts bound how long that lock is held. A write the server makes for itself, such as the bootstrap policy, is not sent.
- **A mutated update.** A mutating webhook that changes an update is held to the same rules as the caller: a change to a field the write may not touch is `Invalid` after the patch, not accepted.
- **Custom resources.** An object of a custom kind is sent with its definition's group, version, kind and plural.

### Running

`Run` takes a listener, a configuration and a context, and serves until the context ends, then stops accepting and drains for a short time. Without the TLS files the server serves plain HTTP and `Run` refuses a listener that is not on a loopback address. With them it serves TLS on any address, loopback included: the server speaks TLS 1.3 or later and verifies a client certificate, against the client CA, when one is given without requiring one ([ADR 0005](./adr/0005-the-api-server-serves-beyond-loopback-only-with-mutual-tls.md), narrowed by [ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md)). The binary reads the etcd endpoints, the listen address, the dial timeout, the etcd TLS files, the TLS files and the bootstrap token file from flags and defaults to loopback for the listener.

- `--tls-client-ca`, `--tls-cert` and `--tls-key` are the PEM files of the client CA and of the server's certificate and key. All three are given or none is, and a partial set, or a file that does not load, stops the server at start.
- The certificate's subject CN is the caller's user, a Node Agent's being its Node name, and the Organization values of its subject are its groups. What the server does with them depends on `--authorization-mode`.
- **Callers, told apart before a request is routed** ([ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md)):
  - A request with a verified certificate is served as every request was under ADR 0005.
  - A request with no certificate and a valid bearer token has the identity `bootstrap:<id>` and may reach only the create and the read of one CertificateSigningRequest. Any other route is `Forbidden`, and so is reading a request whose `spec.username` is another identity. Routes are allowed to a token one by one: a route added later is closed to it.
  - A request with no certificate and a valid service account token has the identity `gaon:serviceaccount:<name>`, no groups, and is authorized like a user. The token is valid where its signature verifies against a key the server holds, its `iss` is the configured issuer, its `aud` holds one of the API audiences, `exp` has not passed, and the MicroVM it names exists with the uid it names; the server reads that MicroVM from the Store for every request. A token that does not hold, or whose MicroVM is gone, is `Unauthorized`; a Store error is an error, not `Unauthorized`. A token minted for another audience is `Unauthorized`.
  - A request to `GET /.well-known/openid-configuration` or `GET /openid/v1/jwks` is served before any of this, with no identity, where an issuer is configured. Without one the paths are not routed and a caller with no certificate is `Unauthorized`.
  - A request with no certificate and a missing or invalid token is `Unauthorized`. The server compares the token's secret in constant time.
  - Plain HTTP authenticates nobody and honours no token, so a request created there has an empty `spec.username`, which the signer's rule denies.
- **`--authorization-mode`** is `AlwaysAllow`, the default, or `RBAC` ([ADR 0008](./adr/0008-the-api-server-authorizes-certificate-callers-with-cluster-roles-bindings-and-a-node-authorizer.md)); any other value, including one in another case, stops the server at start. `RBAC` without the three TLS files stops it at start too, because a request without a client certificate has no identity to authorize.
  - **`AlwaysAllow`** serves every request as ADR 0005 did. ClusterRoles and ClusterRoleBindings can be written and read, and decide nothing; the server creates none.
  - **`RBAC`** authorizes every request made with a certificate. The order is fixed: the Node authorizer first, then the ClusterRoles bound to the caller's user or to one of its groups. The Node authorizer never refuses; a request it does not allow goes to RBAC, and a request neither allows is `Forbidden`, 403. A Node may read Volumes, write the `status` of a Volume pinned to it or used by a MicroVM bound to it, and `PUT` a Volume pinned to it only where the body differs from the stored Volume in the node-agent finalizer alone; it creates and deletes none. The Volume rule is the MicroVM's, and a role that grants `update` on `volumes` is not held to it. A `PUT /microvms/{name}` update from a caller whose only grant is the Node authorizer's is `Forbidden` unless the body differs from the stored MicroVM in `metadata.finalizers` alone, and there only by adding or removing `compute.gaon.garam.sh/node-agent` (the contract's invariant 3); the status and the fields the server sets are not compared, and a caller with `update` on `microvms` from a role is not held to this. A request is its verb, its API group and its resource with the subresource, as ADR 0008 Decision 4 describes it: a `PUT` is `create` where its body carries no `resourceVersion` and `update` where it does, a read of a collection is `list`, or `watch` with `watch=true`. The server reads the roles and bindings from the Store for every request, so an edit takes effect on the next one.
  - **The Node authorizer's Secret, ConfigMap and token rules** (ADR 0020 Decision 17). A Node may `get` a Secret or ConfigMap only where a MicroVM bound to it references it, and may not list or watch either. It may `create` a token only for a MicroVM bound to it, naming the MicroVM's uid and its service account; any other token request from a Node goes to RBAC.
  - **The Node authorizer's Service rules.** A Node may `get`, `list` and `watch` Services, Endpoints and NetworkPolicies, and writes none; a Node certificate of a Node that does not exist is not a Node, and goes to RBAC.
  - **A service account token holder** is the user `gaon:serviceaccount:<name>` with no groups: the Node authorizer allows it nothing, and RBAC judges it by the ClusterRoles bound to that user, label selectors included. In `AlwaysAllow` it is authenticated and allowed.
  - **A bootstrap-token holder** is not authorized by either: the routes of ADR 0007 are the whole of what it may do, and no role widens or narrows them.
  - **The escalation rule** is checked before a ClusterRole or a ClusterRoleBinding is written. A role is refused as `Forbidden` unless the caller holds every permission its rules grant, a binding unless the caller holds every permission of the role it references, and `*` is held only by a rule that has `*`. A rule with a selector is held only through a rule of the same groups, resources and verbs that has none or whose selector contains the new one's, and a rule without one only through a rule without one. A binding whose `roleRef` names no ClusterRole is `Invalid`. A delete needs only `delete`, and the permissions the Node authorizer gives a caller are not counted as held. A refused write stores nothing.
  - **The label-selector rule** ([ADR 0018](./adr/0018-metadata-gains-uid-labels-and-owner-references-lists-take-a-label-selector-lease-and-event-are-new-kinds-and-a-role-rule-may-carry-a-label-selector.md)) is judged by the RBAC authorizer one rule at a time. A rule without a selector allows as before. For a rule with one, a `get` and a `delete` are judged on the stored labels, read from the Store for the request, and an object that does not exist has none. An `update` is judged on the stored labels and on the labels of the request body, a `create` on the labels of the body, and a subresource on the stored labels. A `list` or a `watch` is allowed only where the request's selector selects nothing the rule's does not, and the server does not filter an answer to the rule. The stored labels are read from the key of any kind by its group and plural, so a custom kind is judged as a built-in one. The check that a Node may only change its finalizer of a MicroVM or a Volume does not hide a selector rule: a role that grants `update` with a selector allows a full update only inside it.
  - **The bootstrap policy** is created at start in `RBAC` mode: the ClusterRoles `gaon:scheduler` (which reads `microvms`, `nodes` and `volumes`, and takes the coordination Lease), `gaon:controllers` (which reads and deletes every resource, creates and updates `endpoints` and takes the coordination Lease, [ADR 0021](./adr/0021-the-bootstrap-roles-give-the-scheduler-and-the-controllers-the-coordination-lease-and-the-controllers-read-and-delete-every-resource.md)) and `gaon:admin`, and a binding of each to the group `gaon:schedulers`, `gaon:controllers` and `gaon:admins`. An object that exists is never overwritten, so an operator's edit survives a restart, and one that is missing is created again.
- **`--service-account-issuer`** and **`--service-account-signing-key-file`** are the `iss` of the tokens and the PEM file of the ECDSA P-256 private key that signs them (an `EC PRIVATE KEY` or a PKCS8 `PRIVATE KEY`). Both are given or neither, and a partial set, or a key that does not load or is not P-256, stops the server at start. The issuer is an `https` URL of a host with no path, query or fragment, because the discovery document is served at the issuer's well-known path; it is the same on every API server, the stable address of the control plane. With them the server serves the discovery document and the key set and authenticates service account tokens (resource-api.md §Secret, ConfigMap and ServiceAccount). Without them the token route answers 500, no token authenticates, the discovery paths are not served, and every other route is served.
- **`--service-account-verify-key-files`** is a comma-separated list of PEM files, each of `PUBLIC KEY` blocks of P-256 keys. The server publishes these keys in the key set and accepts tokens they verify, beside the public half of the signing key. It is given only with the issuer and the signing key; a file that does not load, holds another type of block or another curve stops the server at start.
- **`--api-audiences`** is a comma-separated list of the audiences the server accepts in a service account token; a token is authenticated only if its `aud` holds one of them. It defaults to the value of `--service-account-issuer`. It is given only with the issuer and the signing key, and stops the server at start without them.
- **`--etcd-ca-file`**, **`--etcd-cert-file`** and **`--etcd-key-file`** are the PEM files of the CA that signs etcd's certificate and of the client certificate and key the server presents to etcd. All three are given or none, and a partial set stops the server at start with a message naming each missing flag. With them the server verifies etcd against the CA and speaks TLS 1.3 or later, so an `https://` endpoint works and a CA that did not sign etcd's certificate stops the server at start; without them it dials as it did and an `http://` endpoint works.
- **`--etcd-keepalive-time`** (10s) and **`--etcd-keepalive-timeout`** (5s) make the etcd client ping a connection that has a request in flight after that much silence, and drop it if no answer comes within the timeout. A member that stopped without closing its connections, as a stopped host does, then holds a request for at most their sum, 15s with the defaults, before it fails as a 500; the client has by then left that member, and the next request goes to another one. A negative value, or a time without a timeout, stops the server at start, and `0` for both sends no ping, which leaves a request to such a member waiting until its own deadline. The members' `--grpc-keepalive-min-time` (5s by default) refuses a ping more often than it allows, so a time below it needs the members' value lowered. The ping covers requests in flight, not a connection with none: a stream such as a watch is covered, an idle connection is found dead by the first request that uses it.
- **`--service-cluster-ip-range`** and **`--load-balancer-pool`** are the ranges a Service's addresses are allocated from: the virtual service prefix, and the pool of LAN addresses. Each is a CIDR in canonical form, with no host bits, of global unicast addresses, IPv4 or IPv6; neither is required. Two that overlap, or one that does not parse, stop the server at start, before it dials etcd. All API servers of a cluster are given the same values. Without a flag, a create that needs an address of that range is answered with 500.
- **`--bootstrap-token-file`** is a file of valid tokens, one per line, read once at start; blank lines are ignored and removing a token takes effect at the next start. A line that is not a token, a file that cannot be read, and the flag without the three TLS files stop the server at start.
- **CertificateSigningRequest.** A create sets `spec.username` from the caller's identity and drops any status it carries. A `PUT` that carries `metadata.resourceVersion` is `Invalid`, because the spec is immutable. The status path stores the conditions and the certificate under `ValidateStatus`, by compare-and-swap. List and watch are not open to a token holder.
- The server reads the files once at start. It dials etcd at start, trying each endpoint, and fails if none answers. Once it serves, a stopped member costs the requests in flight to it the bound under `--etcd-keepalive-time`, and nothing after that.

## Rationale

- Mutual TLS beyond loopback, the certificate's CN as identity, and authentication without authorization: [ADR 0005](./adr/0005-the-api-server-serves-beyond-loopback-only-with-mutual-tls.md). The authorization modes, the Node authorizer ahead of RBAC, the bootstrap roles and the escalation rule: [ADR 0008](./adr/0008-the-api-server-authorizes-certificate-callers-with-cluster-roles-bindings-and-a-node-authorizer.md). The labels, the uid, the selector rule of RBAC and the two new kinds: [ADR 0018](./adr/0018-metadata-gains-uid-labels-and-owner-references-lists-take-a-label-selector-lease-and-event-are-new-kinds-and-a-role-rule-may-carry-a-label-selector.md). The scheduler's and the controllers' bootstrap rules as they stand: [ADR 0021](./adr/0021-the-bootstrap-roles-give-the-scheduler-and-the-controllers-the-coordination-lease-and-the-controllers-read-and-delete-every-resource.md). The bootstrap token and the narrowed listener: [ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md).
- The Store is etcd, and `resourceVersion`, compare-and-swap and watch map onto etcd's revisions, transactions and watches: [ADR 0004](./adr/0004-the-store-is-etcd-in-one-cell-of-one-member.md). Keeping the Store behind an interface of keys and revisions keeps the rules testable against a real etcd without the rules knowing it.
- One writer per section, and the Lease and the epoch as the fence against a stale writer: [ADR 0003](./adr/0003-the-v1alpha1-resource-api-fixes-one-writer-per-section-and-a-per-node-lease.md). The server holds the invariants the contract gives it; it does not duplicate the rules that `lib/api` owns, so a client and the server cannot disagree about them.
- A user-registered kind is served from the definition read at each request, so a definition's change takes effect on the next one: [ADR 0009](./adr/0009-a-user-registers-a-resource-kind-with-a-customresourcedefinition-the-api-server-serves-it-under-its-own-group.md).
- Webhooks are called from each write in the service, not from a Store decorator, which could not tell a user's operation from one the server makes for itself, and not from the transport, which cannot run the server's own validation between the two stages: [ADR 0010](./adr/0010-a-user-registers-admission-webhooks-with-webhook-configurations-the-api-server-calls-them-on-every-accepted-write.md).
- The server is its own module with its own binary, a unit of the workspace: [ADR 0001](./adr/0001-the-repository-is-a-go-workspace-of-executable-units-partitioned-by-responsibility.md). It imports `lib/api` and nothing else of gaon.
- Three API server processes run over one etcd, and over a three-member cluster with one member stopped; the server starts if any endpoint answers, and holds no state of its own that another process would not have: [ADR 0023](./adr/0023-the-control-plane-runs-on-three-nodes-over-a-three-member-etcd-and-the-scheduler-and-the-controllers-act-only-while-holding-a-coordination-lease.md).
- Tests run the server over an embedded etcd member started in the test process, because no etcd binary is assumed on a developer machine or a CI runner. The etcd server module is a dependency of the tests only; the binary links the etcd client alone. The module is on `go 1.26.0`, as is the workspace, and pins etcd 3.6.16, the newest 3.6 release, with `golang.org/x/net` 0.62.0 and `google.golang.org/grpc` 1.83.2 that it requires. Release 3.6.4, the first pin, carried a client that reached vulnerable code in x/net and grpc from the shipped binary, and the releases that fix them need Go 1.25 or later, which is why the workspace's Go version moved. `govulncheck` over the module reports nothing under Go 1.26.11 and reports only standard library findings under 1.26.0, so the workspace's `toolchain` directive in `go.work` names a 1.26 patch release, which CI and a developer's `go` command build with, and the owner of `go.work` moves it by hand. The pin moves with the Dependabot entry for the module, and with the workspace's Go version.

## Open questions

- **A delete cut short.** A crash after a definition is marked terminating, and before its objects are gone, leaves it terminating and its objects deleting; nothing finishes it until the delete is repeated or an object's last finalizer is cleared.
- **Finalizers on a definition.** The server sets the deletion timestamp of a definition and does not honour a finalizer on it.
- **Authorization by field beyond the MicroVM and Volume finalizer.** In `RBAC` mode the server checks the path an identity may write, and for `PUT /microvms/{name}` and `PUT /volumes/{name}` the part of the body it changes; no other write is checked by field. In `AlwaysAllow`, the default, any authenticated caller may write any path.
- **A binding that names many Volumes.** The binding's transaction holds one compare per Volume the MicroVM uses and one for the MicroVM. etcd limits the operations of a transaction, 128 by default, so a MicroVM that names that many Volumes would get an etcd error, answered as `Internal`, and not a binding. The server does not check the count and no test reaches it.
- **Node created with `spec.admitted` true.** The server starts every Node `Discovered`, so one created already admitted waits for the Node Agent to move its state. The contract does not say whether a create may carry `admitted`.
- **The `Deleted` event.** It carries the last stored value, not the resource as the delete left it, so a consumer sees the finalizer-free state only through the preceding `Modified`. The contract does not say which a consumer should expect.
- **Compaction.** Nothing compacts etcd yet. A watch expires only when an operator compacts, and a cell that is never compacted grows without bound.
