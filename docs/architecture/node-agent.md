# Node Agent

What `gaon-node-agent` does on a node: it registers the node, keeps its Lease and mvmd's fencing deadline renewed, runs the MicroVMs bound to it on mvmd, and reports their status.

Basis: [resource-api.md](./resource-api.md) for the contract it keeps, [ADR 0002](./adr/0002-gaon-owns-the-node-agent-and-depends-one-way-on-mvmd-and-naru.md) for the boundary. The mvmd statements below hold for garamsh/mvmd at commit `3b37892f303a4d4dbd8e5360906d0f9c036b562e`, runtime API `v1alpha2`, which the agent reaches only through mvmd's `lib/runtimeapi` module over mvmd's Unix socket. The MicroVM prefixes statement holds at `d189133bba8d842d2bcb20046f39fe03161efeb1`, the same API version. The network policy and disk statements hold at `3f6e60567966819ba920709a1fe84e9a3848a523`, the same API version ([ADR 0012](./adr/0012-the-node-agent-asks-a-network-plugin-and-a-storage-plugin-compiled-into-it-before-it-creates-a-machine.md), whose compiled-in decision [ADR 0019](./adr/0019-the-node-agent-reaches-its-network-and-storage-plugins-as-separate-processes-through-a-versioned-grpc-api-on-unix-sockets.md) supersedes). The process statements (command, args, env, user, files) hold at `223e3eca764c`, the same API version, whose fields 10 to 14 of the create request carry them. The statements on `working_dir` at create and on `run_update` at a start hold at `80f59a88c601989be628520d3e0ce10f8c8c8f1f`, the same API version, mvmd ADR 0052 and mvmd's `docs/architecture/runtime-api.md`: a run update's env and files replace the machine's wholesale for that start and the starts after it. The `WriteFile` statements (the token and the files replaced in a running MicroVM) hold at `223e3eca764caf60b8dd72c7399b83ff6b437d49`, read in mvmd's `lib/runtimeapi` and in its guest agent's `files.rs`: the new content is committed whole at a clean end of the stream by a rename at the same path, and a stream that breaks leaves the old content.

## Current decisions

### Configuration

Every value is a flag with an environment variable as its fallback. A flag given wins over the variable, and the variable over the default. The agent refuses to start when a required value is missing or the durations do not fit each other, defaults included: the defaults satisfy both inequalities below.

| Flag | Environment variable | Default | Meaning |
|---|---|---|---|
| `--api-server` | `GAON_API_SERVER` | none, required | root URL of the resource API: the API server's address with `/apis/compute.gaon.garam.sh/v1alpha1`, which [resource-api.md](./resource-api.md) §Paths are relative to |
| `--tls-ca` | `GAON_TLS_CA` | none | file of the CA certificates the API server's certificate must chain to |
| `--tls-cert` | `GAON_TLS_CERT` | none | file of the client certificate the agent presents to the API server |
| `--tls-key` | `GAON_TLS_KEY` | none | file of the key of the client certificate |
| `--bootstrap-token-file` | `GAON_BOOTSTRAP_TOKEN_FILE` | none | file holding one bootstrap token, `<id>.<secret>`, with which the agent asks for its client certificate ([ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md)); needs `--cert-dir` and `--tls-ca` |
| `--cert-dir` | `GAON_CERT_DIR` | none | directory where the agent keeps its issued certificate and key in one file, `node-agent.pem`; needs `--tls-ca` |
| `--node-name` | `GAON_NODE_NAME` | none, required | name of this node's Node and Lease |
| `--mvmd-socket` | `GAON_MVMD_SOCKET` | none, required | path of mvmd's runtime API socket |
| `--delta` | `GAON_DELTA` | 1s, provisional | δ, how long a MicroVM can run past mvmd's recorded deadline expiry |
| `--lease-duration` | `GAON_LEASE_DURATION` | 30s | validity of the Lease after a renewal, a whole number of seconds |
| `--renew-period` | `GAON_RENEW_PERIOD` | 5s | time between renewal rounds |
| `--deadline-length` | `GAON_DEADLINE_LENGTH` | 15s | length each deadline renewal asks mvmd for |
| `--rpc-timeout` | `GAON_RPC_TIMEOUT` | 2s | bound on each call of a renewal round |
| `--resync-period` | `GAON_RESYNC_PERIOD` | 10s | time between two reconciliations of the MicroVMs and two reports of the Node's status |
| `--restart-backoff` | `GAON_RESTART_BACKOFF` | 10s | wait before the first restart of a MicroVM, doubled for each restart after it |
| `--restart-backoff-max` | `GAON_RESTART_BACKOFF_MAX` | 5m | cap on the wait between two restarts, not below the backoff |
| `--restart-reset-after` | `GAON_RESTART_RESET_AFTER` | 10m | how long a MicroVM must have run for the wait to start over at the backoff |
| `--plugin-dir` | `GAON_PLUGIN_DIR` | `/run/gaon/plugins` | the directory the plugins serve their sockets in |
| `--network-plugin` | `GAON_NETWORK_PLUGIN` | none | the name of the network plugin, the process serving `<plugin-dir>/network-<name>.sock`; empty names no plugin; a name that cannot be in a socket path refuses the start |
| `--storage-plugin` | `GAON_STORAGE_PLUGIN` | none | the name of the storage plugin, the process serving `<plugin-dir>/storage-<name>.sock`; empty names no plugin; a name that cannot be in a socket path refuses the start |
| `--service-account-audience` | `GAON_SERVICE_ACCOUNT_AUDIENCE` | none | the audience a MicroVM's ServiceAccount token is requested with: one of the API server's `--api-audiences`, which default to its issuer URL; while empty, a MicroVM that names a ServiceAccount is not created and is retried at every resync |

The three TLS values are given together or not at all. All three give a mutual TLS 1.3 client built by `lib/api` that trusts only the CA file; none gives plain HTTP, for a loopback API server; one or two refuse the start, naming the ones missing, as does a file that cannot be read or does not fit. The agent builds its client once at start, so a replaced file is read at the next start.

[ADR 0007](./adr/0007-a-node-gets-its-client-certificate-from-gaons-own-ca-through-a-signing-request-a-bootstrap-token-may-create.md) decides how the agent gets its certificate without operator-supplied files. The agent keeps its own pair when `--cert-dir` is given, with or without `--bootstrap-token-file`, and does this:

- **Flags.** `--bootstrap-token-file` and `--cert-dir` exclude `--tls-cert` and `--tls-key`: the agent takes its certificate from one set or the other, and giving both stops the start naming both sets. `--bootstrap-token-file` without `--cert-dir`, and either without `--tls-ca`, stop the start. The token file holds one token matching `[a-z0-9]{6}\.[a-z0-9]{16}` once surrounding whitespace is trimmed; any other content stops the start, and no message, log line or error carries the token. `--cert-dir` alone is accepted and, with no valid pair in the directory, stops the start.
- **Files.** The agent creates `--cert-dir` with mode 0700 if it is missing. It keeps the pair in one file, `node-agent.pem`, mode 0600, holding the certificate block followed by the key block. The file is written to a temporary file in the directory and renamed into place with one rename, so the directory holds the old pair or the new one whole and a file is never rewritten in place. The agent then syncs the directory, so a pair is durable once written: it survives a power cut, and a failed sync is a failed write, so the pair is not used and a renewal is asked for again.
- **Valid pair.** The file parses, the key matches the certificate, the certificate's common name is `--node-name`, and its `NotAfter` is in the future. At start the agent uses a valid pair, without a token, and renews it as below. Without a valid pair it bootstraps with the token, and without a token the start stops.
- **A request.** The bootstrap and every renewal generate a new ECDSA P-256 key and a `CertificateSigningRequest` named `<node-name>-<16 random hex digits>` whose request carries the node name as common name, the Organization `gaon:nodes` and no other subject attribute, and no subject alternative name ([ADR 0022](./adr/0022-a-nodes-certificate-carries-the-organization-gaon-nodes-and-the-signer-signs-no-other-organization.md)). The agent reads the request every second until it is Approved with a certificate or Denied. The bootstrap calls carry the token and no client certificate; renewal calls present the current certificate and no token.
- **Outcomes.** A Denied request at bootstrap stops the start with the reason, and so does any other error of the bootstrap. A renewal that is Denied or fails is logged, the pair in use stays in the directory and in memory, and the agent asks again after one minute. The pair is replaced only by a certificate received.
- **Renewal.** It is due at `NotBefore` plus two thirds of the validity, and at once when that time has passed at start. The new pair replaces the old one in the TLS client's `GetClientCertificate` callback under a lock, so no restart is needed. A pair issued before ADR 0022 has no Organization: it is valid, and the renewal due for it replaces it with one that has the Organization. A connection already open keeps the pair it was made with; each connection made after the swap presents the new one.

The files given as `--tls-cert` and `--tls-key` are still read once at start and are not renewed.


δ's default of 1s is provisional: it is not measured, in mvmd either, and it is far above a real-time thread's wake-up and a SIGKILL (mvmd ADR 0003). The durations must satisfy two inequalities, checked at start: the deadline length exceeds the renew period plus two call timeouts, so the deadline never lapses between rounds, and the Lease duration is at least the deadline length plus δ plus two call timeouts, so a round can always renew the deadline.

### Registration

- The agent creates its Node with an empty `spec`, by a `PUT` without a version, when the API has none, and never writes `spec` again.
- The Node comes first. Until the API has it, the agent retries the create every resync period and makes no other request that needs it: not the MicroVM list or watch, not a Lease write, not a Node status write. A restarted agent whose Node exists reads it and starts the rest at once. The certificate renewal does not need the Node and runs throughout. Under `RBAC` the Node authorizer allows a Node's MicroVM reads only once a Node of its name exists, and a Lease named as no Node is `Invalid` ([resource-api.md](./resource-api.md) §Authorization), so a request made earlier is refused.
- It writes the Node's `status` by compare-and-swap on every resync: `state` is `Admitted` when a user has set `spec.admitted` and `Discovered` otherwise, `capacity` comes from mvmd's runtime info (cpus as a whole number, memory and storage in bytes, storage being mvmd's state total), `microvmPrefixes` is the runtime info's `machine_prefixes`, and the `Ready` condition is true while mvmd answers. A Node whose mvmd reports no prefix has none. A reported prefix that is not a CIDR is logged at warn level with the prefix named, and is not written; the others are. When mvmd's runtime info fails, the agent writes `Ready` false with reason `RuntimeUnreachable` and the error as the message, keeps the stored `capacity` and `microvmPrefixes`, and keeps the condition's transition time while its status and reason are unchanged.
- It creates the Lease named as the Node on its first round and renews it by compare-and-swap, writing the node as holder.

### Finalizer

- The agent's finalizer is `compute.gaon.garam.sh/node-agent`.
- **Added** to `metadata.finalizers` before the agent first creates or starts a MicroVM bound to its Node, so a MicroVM that is not yet finalized is never run.
- **Removed** once a MicroVM bound to its Node with `deletionTimestamp` set is released on mvmd. Released means mvmd holds no machine the agent named after it, under any epoch, by the round's listing of mvmd less what the round removed. A failed stop or delete keeps the finalizer, and the next resync tries again. A MicroVM bound to another Node keeps the finalizer, since that Node's agent releases it.
- Both are `PUT /microvms/{name}` by compare-and-swap on the version read, changing only the agent's own entry of `metadata.finalizers` and never another's. A conflict is read again and retried, up to three times a round. The API server removes the MicroVM on the write that clears its last finalizer.

### The fencing obligation

- **One loop** renews the Lease first and then, in the same round, mvmd's deadline.
- **Validity of the Lease** is counted from the start of the latest acknowledged renewal call on the agent's monotonic clock, as [resource-api.md](./resource-api.md) states.
- **A deadline renewal is sent only if, were mvmd to receive it as late as the call timeout allows, its expiry plus δ is within that validity.** That is the clock reading now, plus the call timeout, the deadline length and δ, no later than the validity. This bounds a renewal whose acknowledgement never arrives, which resource-api.md leaves to this document: mvmd may have recorded it, and it was recorded no later than the call timeout after it was sent.
- **When the Lease cannot be renewed**, validity stops growing, the check refuses every further deadline renewal once the margin is gone, and mvmd's deadline lapses on its own. The MicroVMs are fenced by mvmd, not by the agent's survival. A failed Lease call makes the agent read the Lease again before the next write.
- **Every call of a round is bounded** by the call timeout, including the read of mvmd's last applied number, so a runtime that does not answer ends the round with an error and the next round renews the Lease.
- **The renewal number** sent to mvmd increases monotonically; the agent reads mvmd's last applied number once at start, so a restarted agent continues the sequence.
- mvmd refuses to start or restore a MicroVM while its deadline is not armed or has expired; the agent treats that refusal as a failure to retry on the next resync, and the MicroVM stays `Pending`.

### Plugins

[ADR 0019](./adr/0019-the-node-agent-reaches-its-network-and-storage-plugins-as-separate-processes-through-a-versioned-grpc-api-on-unix-sockets.md) makes the network and storage plugins processes of their own, which supersedes the compiled-in plugins of [ADR 0012](./adr/0012-the-node-agent-asks-a-network-plugin-and-a-storage-plugin-compiled-into-it-before-it-creates-a-machine.md). The agent reaches each by gRPC over a Unix socket, through the client in `lib/plugin`; nothing plugin-specific is compiled into `node-agent/`. The API, `gaon.plugin.v1alpha1`, is documented in `lib/plugin/README.md`.

- **Discovery:** `--network-plugin <name>` and `--storage-plugin <name>` name the plugin whose socket is `<plugin-dir>/<kind>-<name>.sock`, `kind` being `network` or `storage`. A socket path over 107 bytes, the 108 of a Linux Unix socket path less its terminating NUL, is refused with an error naming that limit: by the agent and by a plugin at its start, not left to fail at bind. There is no scan and no registry. The agent dials lazily, so it starts with a plugin not running. With no network plugin named a MicroVM is created with the empty policy, which mvmd reads as blocking all outside traffic; with no storage plugin named no disk is attached and a MicroVM that names a Volume fails with `NoStoragePlugin`.
- **Order:** for a MicroVM to create, the agent asks the network plugin for the policy, pulls the image, asks the storage plugin to attach the volumes, and creates the MicroVM in mvmd with the policy and disks in the one request, then starts it. No MicroVM is started without its policy, which keeps invariant 6.
- **Refusal:** a plugin refuses a MicroVM with a reason and a message, carried in the response and not as a gRPC error. The MicroVM is `Failed`, its `Ready` condition false with that reason and message, and mvmd is not asked to create it. Any other plugin error is retried at the next resync.
- **A plugin that is not running:** a call that gets gRPC `Unavailable`, or `Unimplemented` from a plugin that does not serve this API version, or that is not answered in 10 seconds, is not a refusal. The MicroVM is not created and the call is retried at every resync, so a plugin started later is served by the next one. While it fails the MicroVM is `Pending` with `Ready` false, the reason `NetworkPluginUnavailable` or `StoragePluginUnavailable` and a message naming the error.
- **Enforcing NetworkPolicy:** at the end of every round the agent lists the NetworkPolicies and, when the network plugin enforces them, calls its `Enforce` with the effective limits of each MicroVM bound to this Node that has an address in `status.addresses`. A MicroVM's limit in a direction is unset when no policy selects it for that direction (`EffectivePolicyTypes`), which is unrestricted, and otherwise the union of what every selecting policy allows: one allow for each `ipBlock` (with its `except`), one `/32` or `/128` for each address of each MicroVM a `podSelector` peer selects, and every address for a rule with no peer, each with the rule's ports, or every port when it has none. A policy that selects a MicroVM and has no rules for a direction it limits leaves the limit empty, which allows nothing. `Enforce` is declarative and complete: it carries every limited MicroVM of the Node, and the plugin replaces what it enforced with exactly that, so a deleted policy or MicroVM is lifted by the next call. Unlike `Policy` and `Attach`, a failure of `Enforce` holds no MicroVM ([ADR 0034](./adr/0034-a-network-plugin-may-enforce-networkpolicy-through-an-optional-enforce-call-whose-failure-does-not-hold-a-microvm.md), which departs from ADR 0019 Decision 5 here): the MicroVM is created and run whatever it answers, because the limits come from addresses that exist only once the MicroVM runs. A plugin that does not enforce answers gRPC `Unimplemented`; the agent asks again at every round and the MicroVM runs on the policy it was created with. While a policy selects a MicroVM bound to this Node, that answer is logged as a warning at every round, which is where an operator sees that policies go unenforced; with no such policy it is logged at debug level. Any other error is logged as a warning of the round and retried at the next. The agent re-lists the policies each round and does not watch them, so a change reaches the plugin within one resync or at the next MicroVM event.
- **Serving Services:** at the end of every round, after `Enforce`, the agent lists the Services and Endpoints and, when the network plugin serves them, calls its `Expose`. It carries a route for each port of each Service that has a `clusterIP`, and a route marked LAN for each `status.loadBalancer.ingress` address of a LoadBalancer Service, each with the address, protocol, port and the ready backends, address and target port, that the Service's Endpoints lists for a port of the same name and protocol. A headless Service has no route. It also carries `announce`, the LAN addresses this Node answers for. Every Node gets every route; only `announce` differs. `Expose` is declarative and complete, so a deleted Service or endpoint is withdrawn by the next call. As for `Enforce`, its failure holds no MicroVM ([ADR 0036](./adr/0036-a-network-plugin-may-serve-services-through-an-optional-expose-call-and-the-node-that-runs-the-first-listed-microvm-answers-for-a-lan-address.md)): a plugin that does not serve Services answers `Unimplemented`, which is logged as a warning at every round while a Service has a route and at debug level otherwise, and any other error is logged as a warning of the round and retried at the next. The agent re-lists each round and does not watch, so a change reaches the plugin within one resync.
- **Which Node answers for a LAN address:** the Node whose name sorts first among the Nodes running a MicroVM that the Service's Endpoints lists (`targetRef`, read as the MicroVM's `spec.nodeName`); with none listed, the first among the Nodes running any MicroVM. Each agent decides this from the MicroVMs and Endpoints it lists, so exactly one Node answers and none coordinates; a Node that runs no MicroVM never answers.
- **Release:** the storage plugin's `Release` is called with the mvmd identifier after the agent deletes a microvm, and after mvmd rejects a create. It is repeatable and may be called for an identifier `Attach` never saw.
- **Identity:** a plugin that uses the resource API acts as the Node it serves, presenting the Node Agent's own client certificate (ADR 0019 Decision 6). A narrower plugin identity is for garamsh/gaon#138.
- **Installation:** a plugin is a Node service installed and started by naru, in the way deployment.md §Plugins describes. The agent does not start plugins.
- **`default` network** (`network-default/`, binary `gaon-network-default`, `--network-plugin default`): a MicroVM naming no network or only `default` is served; any other network is refused with `UnknownNetwork`. Egress is one any-protocol rule for each `--egress-prefix` (`GAON_EGRESS_PREFIX`); ingress is a rule for each port of `spec.ports` and each `--ingress-prefix`, with the protocol the port declares (a `UDP` port is allowed as UDP, a `TCP` port as TCP) (`GAON_INGRESS_PREFIX`). Both are repeatable on the plugin's command line, and its variable is comma-separated and replaced by a flag. With no prefixes the policy is empty, which mvmd reads as blocking all outside traffic. A prefix that is not an IPv4 or IPv6 CIDR refuses the plugin's start, and a port outside 1 to 65535 or a protocol other than `TCP` or `UDP` fails the MicroVM with `InvalidSpec`.
- **`default` network enforcement:** it implements `Enforce` in an nftables table of its own, `inet gaon_network_default`, replaced whole in one transaction on every call, so a packet meets the old rules or the new. The table has a `forward` hook at the filter priority, with policy accept, that jumps to an egress chain and an ingress chain. Each chain first returns for packets of an established or related connection, so a connection a policy allowed to begin is not cut in the other direction and no connection state needs tracking by the plugin. For each limited direction of each address it then returns for a peer prefix (less its excepts, which the plugin cuts out in Go) and port that is allowed, and drops the rest to or from the address; an unlimited MicroVM matches no rule and is unrestricted. It needs `CAP_NET_ADMIN` in the Node's network namespace, and touches no other table. `Enforce` is separate from the create-time policy above, which mvmd applies at its own layer: a NetworkPolicy narrows what the plugin lets through the forward hook and does not widen what the create-time policy blocks.
- **`default` network Services:** it implements `Expose` in a second nftables table, `inet gaon_network_default_services`, replaced whole in one transaction on every call, separate from the enforcement table. A prerouting chain at the destination-NAT priority translates a connection to a route's address and port to one of its backends' address and target port, each backend taking an equal share by a random choice; a connection to a LAN route is also marked, and a postrouting chain masquerades marked connections, so a backend on another Node replies through the answering Node. A route with no backend is refused instead, by a filter chain ahead of the translation: a TCP connection is answered with a reset and a UDP packet with an ICMP port unreachable, for the cluster IP and for the LAN address alike, so a Service with no ready Endpoints refuses connections at once. A backend of the other address family than its route's is left out, which leaves the route refusing when all are. The LAN answer is the kernel's: for each address in `announce` the plugin adds a host address (`/32` or `/128`) to `--lan-interface` (`GAON_LAN_INTERFACE`), and the kernel answers ARP and NDP for it; it removes a host address inside `--lan-pool` (`GAON_LAN_POOL`, repeatable, comma-separated in its variable) that is no longer in `announce`, which stops the answer, and leaves every other address of the interface alone. The interface and the pool are given together or the plugin does not start; without them a Service is translated and no LAN address is answered, and an `announce` address is an error. An `announce` address outside the pool is an error and is left out, and the rest of the call still converges, so a stale address is withdrawn and a valid one added in the same call. The plugin owns the whole conntrack mark: it sets `0x67616f6e` on a LAN connection and masquerades every connection that carries it, overwriting any mark another user of the Node set earlier, so no other rule on the Node may use the mark. A connection to a cluster IP is translated and not masqueraded, so a MicroVM that is a backend of a Service it connects to can be translated to itself and then receives the connection from its own address; the plugin does nothing for that case. It needs `CAP_NET_ADMIN` in the Node's network namespace, and touches no table but its two.
- **`local` storage** (`storage-local/`, binary `gaon-storage-local`, `--storage-plugin local`): serves the Volumes of class `local` pinned to this Node ([ADR 0013](./adr/0013-a-volume-is-created-through-its-own-path-a-local-volume-is-a-disk-its-nodes-agent-makes-and-a-binding-pins-it-to-a-node.md) Decisions 2, 4 and 5) as mvmd disks of `spec.storage` bytes, rounded up, named `volume-<Volume name>`, which mvmd formats ext4. It is given `--api-server`, `--node-name`, `--mvmd-socket`, `--resync-period` and the TLS settings, each with a `GAON_` variable, and reads the Node's certificate as the agent does: `--cert-dir` with `--tls-ca` reads `node-agent.pem` at each new connection, `--tls-cert` and `--tls-key` are read once, and none gives plain HTTP.
  - **Attach:** for each Volume the MicroVM names, once, it reads the Volume and refuses the MicroVM before writing anything if the Volume is missing (`VolumeNotFound`), is of another class (`UnsupportedStorageClass`), is being deleted or pinned to another Node (`VolumeNotUsable`), or is attached to another MicroVM at the same or a higher epoch (`VolumeInUse`). It then lists mvmd's disks, creates the disk only if none has the name, and writes the Volume's `status` as `Bound` with the attachment `{microvmName, bindingEpoch}` and the disk's size as `capacity`, by compare-and-swap on the version read; a conflict is read again and decided again, up to three times. A disk mvmd refuses to create, with outcome kind `REJECTED`, `PRECONDITION_FAILED` or `FAILED`, writes the Volume `Failed` and refuses the MicroVM with `VolumeFailed`; any other error is retried at the next resync. A repeated call for the same MicroVM and epoch makes no disk, and writes `Bound` again only if the phase is no longer `Bound`.
  - **Release:** does nothing. The disk lives until its Volume is deleted.
  - **Growth** ([ADR 0040](./adr/0040-a-volumes-storage-may-grow-when-its-class-allows-it-the-provisioner-grows-the-disk-and-a-growth-still-open-shows-as-a-resizing-condition.md) Decisions 4, 5 and 7): at each resync, while a Volume's `spec.storage` is above its `status.capacity` (the disk's size where it has none), it calls mvmd's `ResizeDisk` for the Volume's disk with `spec.storage` in bytes, rounded up. While the growth is open the Volume's `status.conditions` holds `Resizing` with status `True` and the reason `InProgress` (written before the call, unless a `Resizing` condition already stands), `HolderNotResizable` (mvmd answered precondition failed) or `Failed` (any other error, with mvmd's message as the condition's message). The reason follows each answer, and every state is retried at the next resync. On success one status write raises `capacity` to the new size and removes `Resizing`. `status.phase` does not change. mvmd's `ResizeDisk` is in garamsh/mvmd at commit `20150e3ba4dcc7bd860c3d80cb94ee44fd2227ed`.
  - **Status loop:** every resync the plugin lists the Volumes and mvmd's disks and, for each local Volume pinned to this Node and not being deleted, makes the disk if it is missing and writes `status` only when it differs: `Bound` while a MicroVM holds the disk and the Volume has an attachment, `Released` once none holds it and the attachment remains, which is kept, and `Available` with `capacity` while there has been no attachment; a disk that cannot be made is `Failed`. Between `Attach` and mvmd's create the disk is not yet held, so a round there writes `Released`, and the next `Attach` or round writes `Bound` again. A write that conflicts is left to the next round.
  - **Deletion:** a Volume pinned to this Node with `deletionTimestamp` set and the agent's finalizer `compute.gaon.garam.sh/node-agent` has its disk deleted and the finalizer removed once mvmd reports no MicroVM holding the disk. The removal is `PUT /volumes/{name}` by compare-and-swap on the version read, changing only that entry of `metadata.finalizers`; the API server removes the Volume on the write that clears its last finalizer. A disk still held keeps the disk and the finalizer. A disk already absent is not an error. A Volume without the agent's finalizer, or pinned to another Node, is left alone. A deleting Volume whose VolumeSnapshot is not ready and not being deleted keeps its disk and its finalizer, so the snapshot can still be taken from it. So does one whose VolumeSnapshot carries the agent's finalizer and has no `status.nodeName`, being deleted or not, until that finalizer is removed: no other Node may write that snapshot, and the Volume's pin is how this one still does.
  - **Snapshots** ([ADR 0042](./adr/0042-a-volumesnapshot-names-the-volume-it-copies-its-classs-provisioner-takes-it-a-volume-is-created-from-it-by-data-source-and-a-local-snapshot-keeps-its-volumes-on-its-node.md) Decisions 2, 4 and 7): at each resync the plugin lists the VolumeSnapshots. A snapshot that is not ready and not being deleted, whose source Volume (`spec.volumeName`) is of class `local` and pinned to this Node, is taken: while the source has no `status.capacity` its `status.conditions` holds `Snapshotting` with status `True` and the reason `SourceNotReady`, with no finalizer and no call to mvmd. Otherwise the plugin adds the finalizer `compute.gaon.garam.sh/node-agent` by `PUT /volumesnapshots/{name}`, changing only that entry of `metadata.finalizers`, writes `Snapshotting` with the reason `InProgress` (unless a `Snapshotting` condition already stands), and calls mvmd's `SnapshotDisk` for the source's disk with the snapshot identifier `snapshot-<metadata.uid>` and the request identifier `take-snapshot-<metadata.uid>`, the same at every attempt; the uid keeps a snapshot deleted and made again under one name a different mvmd snapshot. The reason follows each answer: `HolderNotSnapshottable` (mvmd answered precondition failed) or `Failed` (any other error, with mvmd's message as the condition's message), each retried at the next resync. On success one status write sets `readyToUse` to `true`, `restoreSize` to the snapshot's size in bytes read from mvmd's `ListDiskSnapshots`, `storageClass` to `local` and `nodeName` to this Node, and removes `Snapshotting`; later rounds leave a ready snapshot alone. A snapshot with no source Volume, an unpinned source, or a source of another class is left unchanged, with no condition. A snapshot with `deletionTimestamp` set and the agent's finalizer, whose `status.nodeName` is this Node (or, where it has none, whose source is a `local` Volume pinned here), has its mvmd snapshot deleted through `DeleteDiskSnapshot`, an absent one not being an error, and the finalizer removed by the same compare-and-swap write; it keeps both while a Volume whose `spec.dataSource` names it has no `status.capacity` and no `deletionTimestamp`, since that Volume's disk is not made yet. A write that conflicts or finds the object gone is left to the next resync. mvmd's `SnapshotDisk`, `ListDiskSnapshots` and `DeleteDiskSnapshot` are in garamsh/mvmd at commit `29ce9e35b190a7819901ab8738b30a886edef5a1`.
  - **From a snapshot** ([ADR 0042](./adr/0042-a-volumesnapshot-names-the-volume-it-copies-its-classs-provisioner-takes-it-a-volume-is-created-from-it-by-data-source-and-a-local-snapshot-keeps-its-volumes-on-its-node.md) Decision 3): a Volume whose `spec.dataSource` names a VolumeSnapshot has its disk made, by the status loop or by `Attach`, with mvmd's `CreateDisk` carrying `from_snapshot_id` set to that snapshot's identifier `snapshot-<metadata.uid>` and `spec.storage` in bytes, so the disk takes the snapshot's filesystem. The API server has pinned the Volume to the snapshot's Node, so the plugin on that Node makes the disk at once, with no MicroVM that uses it, and the status loop writes `Available` with `capacity` as for any disk. A snapshot that does not exist, or has no `metadata.uid`, writes the Volume `Failed` and makes no disk; a disk mvmd refuses is `Failed` as for any Volume. A Volume with no `dataSource` is made with no `from_snapshot_id`.

### MicroVMs

- **Watched set:** the agent lists the MicroVMs, watches from the list's version and reconciles on every change and every resync. A failed or expired watch is followed by a new list.
- **Identity in mvmd:** a MicroVM is held in mvmd as its name with the binding epoch appended. A binding at a later epoch is therefore a different mvmd machine, and the earlier one is removed, never reused.
- **Kernel:** the agent passes `spec.kernel` unchanged as the create request's `kernel`, so an empty value leaves mvmd to pick the node's default.
- **Epoch rule:** the agent keeps the newest epoch it has seen for each MicroVM and ignores an event, a list entry or a re-read carrying an older one.
- **Run:** a MicroVM bound to this node, not being deleted and not `OnDemand`, has its image pulled by digest, is created in mvmd and started, according to `runStrategy`: `Halted` is stopped and not created, `Once` is not started again after it stopped, unless the agent stopped it for `Halted` and `runStrategy` is now `Once`, which starts it, the others are started whenever mvmd holds them created, and restarted as below when it holds them stopped or faulted.
- **Process:** the agent passes `spec.command` as the create request's `command`, `spec.args` as `args`, `spec.user` as `user`, each `spec.env` entry as an `EnvVar` in order, and each `spec.files` entry as a `File` with its path, content, mode and owner. A file's mode is its own, else `0644`. A file's owner is its own `owner`, else the MicroVM's `user` when that is a numeric `uid:gid`, else root when the MicroVM gives no user. A file that gives no owner under a user that is not a numeric `uid:gid` fails the MicroVM as `InvalidSpec`, since the agent cannot resolve a name in the guest's user database. `args` without `command` is passed as is; mvmd then replaces the image's command, and refuses it with `FAILED_PRECONDITION` for an image pulled before mvmd kept an entrypoint and a command apart, which the agent reports as `Failed` with the reason `PreconditionFailed` and mvmd's message. The agent passes `spec.workingDir` as `working_dir`; mvmd refuses one that is not absolute and clean, which the agent reports as `Rejected`.
- **References:** an env entry or a file with `valueFrom` is resolved by a `get` of the named Secret or ConfigMap under the Node's own identity, at the moment the agent creates the MicroVM in mvmd, and again at each start of a machine it already holds (§Run strategy and resolution). The agent reads each object once per create and once per such start, and again once per resync for a file's reference while the MicroVM runs (§Token and files in a running MicroVM). It never lists or watches one, which the Node authorizer allows only for objects a bound MicroVM references ([ADR 0020](./adr/0020-a-microvm-takes-a-process-ports-files-and-probes-secret-configmap-and-serviceaccount-are-kinds-and-a-token-request-returns-a-jwt-bound-to-a-microvm.md)). A missing Secret, ConfigMap or key fails the MicroVM as `Failed` with the reason `ReferenceNotFound` and a message naming the object and key. Any other error from the `get` is retried at the next resync and leaves the MicroVM as it was.
- **Bounds:** the agent holds the resolved files, and the token file when there is one, to `api.MaxFiles` (64) and `api.MaxFilesBytes` (1 MiB of content in all). Over either, the MicroVM fails as `Failed` with the reason `FilesOverBound` before `CreateMachine` is called.
- **Secret values:** no value of a Secret, nor of a ConfigMap, nor a ServiceAccount token, is written to a log line, an event, a status message or an error: those name the object, the key, the file path or the variable name and never the value, and the agent's log of a create states counts only.
- **Run strategy and resolution:** `runStrategy: Always` restarts the guest, through mvmd's `StartMachine` of the machine it already holds. `status.bindingEpoch` does not change at a restart, since the machine is the same. At every start of a machine it already holds, whether a restart after an exit, the start of a `Halted` MicroVM set to `Always` or `Once`, or a start of a machine mvmd holds created, the agent resolves env and files again and gives them to mvmd as the start's `run_update`, which replaces what the machine holds (mvmd ADR 0052). The token file is among the files, with a token asked for again, so the guest boots with a new token and the token's renewal runs from that start. A Secret or ConfigMap changed since the last start therefore reaches an env entry and a file at the next start; a running guest still gets a changed file by the replacement below and never a changed env entry. A reference that no longer resolves at such a start fails the MicroVM with `ReferenceNotFound`, as at create: mvmd is not asked to start, the machine stays as it is, and the agent tries again at each resync, so the MicroVM runs once the reference resolves.
- **Token and files in a running MicroVM:** per [ADR 0029](./adr/0029-a-microvms-serviceaccount-token-is-a-file-at-a-fixed-path-and-the-node-agent-replaces-it-and-the-files-that-reference-a-secret-or-configmap-in-place-while-the-microvm-runs.md).
  - **Token file:** a MicroVM with `spec.serviceAccountName` has a file at `/var/run/secrets/gaon.garam.sh/serviceaccount/token`, mode 0600, owned as a file that gives no owner is. The agent asks `POST /serviceaccounts/{name}/token` with the audience given by `--service-account-audience` (the API server accepts a token whose audience is one of its `--api-audiences`, by default its issuer URL), the default lifetime and the MicroVM's name and uid, and sends the token in the create request, and in the run update of each start of a machine it already holds, with a token asked for again. A `spec.files` entry at that path fails the MicroVM as `InvalidSpec`, and a ServiceAccount that does not exist as `ReferenceNotFound`.
  - **Renewal:** once 80% of the lifetime has passed on the agent's own clock, counted from its request, the agent requests a token again and replaces the file through mvmd's `WriteFile`: the content is committed whole by a rename at the same path, so a reader sees the old file or the new one. A refused request or write is retried at every resync.
  - **Expiry:** when the token has expired on the agent's clock with no renewal accepted, the MicroVM stays `Running` with `Ready` false and the reason `TokenExpired`, until a renewal is accepted. After an agent restart the expiry of the guest's token is not known, so none is reported until a renewal has been accepted.
  - **Files that reference an object:** at every resync the agent reads each Secret and ConfigMap a `files` entry names, and replaces the file through `WriteFile` when its value differs from the last it delivered. A value that cannot be read, or a write that fails, leaves the file as it was, is logged by name, and is retried. `env` is not replaced.
  - **After a start:** a start of a machine the agent holds boots the guest with the values the run update carried, so nothing is replaced after it. A start at create boots the guest with the create request's token and file values, and after an agent restart the agent does not know what the guest holds, so in both it replaces them at the next resync.
  - **No second process:** nothing runs in the MicroVM beside the workload for any of this; the writes go through mvmd's runtime API.
- **Probes:** the agent passes `spec.readinessProbe` and `spec.livenessProbe` as the create request's `probes`, named `readiness` and `liveness`, with `exec` as `exec`, `tcpSocket` as `tcp` and `httpGet` as `http_get`, and the probes' timing as mvmd's durations and thresholds. A zero field is left unset, which mvmd defaults as gaon does (period 10s, timeout 1s, thresholds 1 and 3, no initial delay). A named `port` is sent as the number of the `spec.ports` entry it names, and an empty `httpGet.path` as `/`. A value mvmd cannot take, such as a period over 24 hours, is not checked by the agent: mvmd refuses the create, and the MicroVM fails as `Rejected` with mvmd's message, which names the probe. A port name `spec.ports` does not declare fails the MicroVM as `InvalidSpec`. mvmd runs the probes and acts on no result: the agent reads the results from `InspectMachine` at each round (the resync, not an event), and acts as follows.
  - **Readiness:** a `Running` MicroVM with a readiness probe is `Ready` true only while mvmd reports the probe passing. While mvmd reports it unknown, or reports no result, `Ready` is false with the reason `ReadinessProbePending`; while it reports it failing, `Ready` is false with the reason `ReadinessProbeFailing` and mvmd's last failure as the message. The phase stays `Running`, and the agent stops nothing for readiness. `TokenExpired` takes precedence. A MicroVM with no readiness probe is `Ready` true while it runs.
  - **Liveness:** when mvmd reports the liveness probe of a `Running` MicroVM failing, the agent stops the machine with the grace period and treats the stop as a failed exit, whatever the entrypoint's record says. Under `Always` and `RerunOnFailure` it is then started again by the restart above, with the same backoff and `restartCount`, and there is no second restart path. Under `Once` the MicroVM is `Failed` with the reason `ExitFailed` and the message `the liveness probe failed: ` and mvmd's last failure, and is not started again. The liveness verdict is cleared at each start. A `Halted` MicroVM is stopped for `Halted` and not for liveness.
  - **Stale results:** in mvmd `eebb760d62370c1ebf49bb86c5a9413d76c71650` (`daemon/internal/machine/probe_follow.go`) `unfollowProbes` drops the held results when a machine leaves Running, a new follower starts from `unknownProbes`, and `probeResultsOf` reports unknown for each probe in any state but Running and Paused, so a result of an earlier run is not read as the next run's. This is read from mvmd's source and not run against a running mvmd.
- **Grace period:** every `StopMachine` the agent sends, for `Halted`, for a liveness failure, for a faulted machine before a restart and for a removal, carries `grace_period`, always set. A MicroVM with no `terminationGracePeriodSeconds` is sent 30 seconds, gaon's default; `0` is sent as an explicit zero duration, which mvmd `eebb760d62370c1ebf49bb86c5a9413d76c71650` takes as sending the Driver's request alone and then ending the VMM, with no wait; `N` is sent as `N` seconds. A removal takes the period from the MicroVM the agent still holds in its cache under that name, else the default. A stop holds the reconcile loop for up to the period, since the agent reconciles one MicroVM at a time. mvmd documents no meaning for an unset period at that commit.
- **Remove:** every mvmd machine the agent named that is not a MicroVM bound here now, whether unbound, bound elsewhere, bound at an older epoch, being deleted or no longer in the API, is stopped and deleted. This also clears what an earlier run left. An mvmd machine whose identifier the agent did not form is left alone.
- **Status:** the agent writes `phase`, `bindingEpoch` equal to the spec's, `observedGeneration`, `addresses`, `restartCount` and a `Ready` condition, only when they differ from what is stored. `lastExit` is never written: mvmd reports no exit time (garamsh/mvmd#331).
- **Restart:** under `Always` a MicroVM that stopped, and under `RerunOnFailure` one that failed, is started again after a wait and not before. The wait is the backoff, doubled for each restart and capped at the maximum, and starts over once the MicroVM has run for the reset time. A clean exit under `RerunOnFailure` is not restarted. A faulted MicroVM is stopped first, since mvmd accepts only a stop in that state. A `Halted` MicroVM resumed is started at once and is not a restart. A MicroVM the agent holds stopped for `Halted` is started at once when `runStrategy` becomes `Once`, and its next exit is judged afresh. The agent knows it stopped the MicroVM for `Halted` from its memory, so after an agent restart a `Halted` MicroVM switched to `Once` is not started.
- **Failure:** the agent reads the entrypoint's record from mvmd, exec `entrypoint`, once when it first sees the MicroVM stopped, under `Once` as under the restarting strategies. The exit failed when the record is `EXITED` with a non-zero exit code or a terminating signal, when there is no `EXITED` record, or when the MicroVM is faulted; an `EXITED` record with code 0 and no signal is clean. A read that returns no record before the call timeout is a failure; any other error leaves the exit unjudged until the next resync.
- **`restartCount`:** each restart adds one, written by compare-and-swap with the MicroVM's epoch checked, so a count of an earlier epoch is never carried into a later one. A write that conflicts is read again and retried, and a restart whose write failed is written by the next round, never counted twice.
- **Where the state lives:** the wait, the streak and the judged exit are kept in the agent's memory per mvmd machine, so a rebinding starts with none; an agent restart forgets them, and a MicroVM it finds stopped then waits the first backoff. The exit time is not known (garamsh/mvmd#331), so the reset time is measured from when the agent started the MicroVM or first saw it running to when it first sees it stopped, which can lag the exit by up to one resync.

| mvmd state | Phase | Ready |
|---|---|---|
| created | `Pending` | false |
| running | `Running` | true |
| paused | `Suspended` | false |
| stopped, `Halted` | `Stopped` | false |
| stopped, `Once`, clean exit | `Succeeded` | false, not started again |
| stopped, `Once`, failed exit | `Failed` | false, reason `ExitFailed` and a message naming the exit, not started again |
| stopped, `RerunOnFailure` after a clean exit | `Succeeded` | false, not started again |
| stopped, other | `Pending` | false, started again once the restart wait is over |
| faulted | `Failed` | false, the reason is mvmd's last failure reason; stopped and started again once the restart wait is over |
| running, token expired in the guest and not renewed | `Running` | false, reason `TokenExpired` |
| running, readiness probe not reported passing | `Running` | false, reason `ReadinessProbePending` or `ReadinessProbeFailing` |
| running, liveness probe reported failing | stopped, then as the run strategy: started again after the backoff, or `Failed` with reason `ExitFailed` under `Once` | false |

- **Failures the agent settles itself** go to `Failed` with the `Ready` condition false and a reason: `InvalidSpec` for an image that is not `<repository>@sha256:<digest>` or resources it cannot convert, `ReferenceNotFound`, `FilesOverBound` and `PreconditionFailed` as under Process, References and Bounds, and `Rejected` for a create mvmd refuses, such as one above a Driver's `max_vcpus` or one naming a kernel the node does not offer, with mvmd's reason as the message. The Driver's limit is not on the Node's status. A network or storage plugin's refusal of a MicroVM fails it with the plugin's own reason and message, and `NoStoragePlugin` fails one that names a Volume when no storage plugin is named.
- **A plugin that is not running** leaves the MicroVM `Pending` with `Ready` false and the reason `NetworkPluginUnavailable` or `StoragePluginUnavailable`, until the plugin answers (§Plugins).
- **Outcome kind `IN_PROGRESS`** is treated as never produced by mvmd (garamsh/mvmd#307).

### What the agent does not do yet

- `OnDemand` MicroVMs, wake and suspend.
- Mounting a Volume at its `mountPath`: mvmd's `DiskAttachment` carries a disk identifier and a read-only flag and no path, so the agent attaches the disk and does not pass the path. Volume classes other than `local` are refused by the `local` plugin or left to a storage plugin that serves them.
- The Node's `addresses` and `agentPort` (the port it is to serve on).
- Serving a MicroVM's log and exec. Decided in [ADR 0043](./adr/0043-a-microvms-log-and-exec-are-subresources-authorized-apart-from-get-and-the-api-server-proxies-them-to-its-nodes-agent-over-mutual-tls.md): a TLS 1.3 listener that accepts only a client certificate of the Organization `gaon:apiservers`, presents its Node certificate, and serves a Machine it holds at the `bindingEpoch` and `uid` the request carries. Its certificate request is then to ask for the extended key usage client auth and server auth, after the signer accepts both ([csr-signer.md](./csr-signer.md)).
- Calling naru.

## Rationale

- One loop for the Lease and the deadline keeps the obligation checkable in one place: the deadline is never renewed outside a round that has just seen the Lease's validity.
- The call-timeout margin pays for not knowing whether an unacknowledged call reached mvmd, instead of asking mvmd afterwards, which a failing path may not allow.
- The restart state is in memory because nothing the contract defines can hold it, and losing it costs one backoff, not a missed restart.
- A clean record equal to the previous one counts as a failure because the cost of a wrong restart is one backoff, and of a wrong stop is a MicroVM that never runs again.
- The exit is read once, at the first sight of the stopped state, so a log that changes afterwards cannot change the verdict.
- The `local` plugin lists Volumes and disks every resync instead of watching because what to write depends on whether mvmd holds the disk, which no Volume event says.
- The plugins are processes because a third party must add a network or a storage system without rebuilding the agent, which is the sign ADR 0012 named; the built-ins are delivered the same way so the API is exercised by what ships. The policy is in the create request because mvmd takes it there, so it cannot be applied late. `Enforce` is a separate call because a NetworkPolicy changes after a MicroVM runs and selects peers by addresses that exist only then, and it does not hold a MicroVM so that an absent enforcer does not stop the cluster, as a Kubernetes cluster whose network plugin ignores NetworkPolicy still runs its pods ([ADR 0034](./adr/0034-a-network-plugin-may-enforce-networkpolicy-through-an-optional-enforce-call-whose-failure-does-not-hold-a-microvm.md)).
- `Expose` is a separate call, complete and without a hold, for the reasons `Enforce` is ([ADR 0036](./adr/0036-a-network-plugin-may-serve-services-through-an-optional-expose-call-and-the-node-that-runs-the-first-listed-microvm-answers-for-a-lan-address.md)): its routes come from Endpoints that change while MicroVMs run. A Service with no endpoint is refused, not dropped, so a client fails at once and does not mistake it for a network fault. The answering Node is a function of the MicroVMs and Endpoints because an agent cannot list Nodes, and it is taken from the Nodes that run the backends so the answer is where the traffic goes anyway. The kernel answers ARP and NDP for an address it holds, so the plugin holds the address and implements no protocol.
- A plugin that is not running leaves the MicroVM `Pending` and retried, not `Failed`, because the plugin may start a moment later and a refusal is the plugin's verdict on the MicroVM, which an absent plugin has not given.
- The plugin names default to none because an agent with nothing installed must still run MicroVMs, isolated; a MicroVM that names a Volume is refused for want of a storage plugin and not silently started without its disk.
- The restart settings are flags with the recorded defaults because the contract fixes no values and a node's operator is the one who knows its workloads.
- The token is renewed at 80% of its lifetime, by the agent's clock and not the answer's expiry, so a workload has a fifth of the lifetime to survive a refused renewal and the two clocks are never compared.
- The agent replaces a file through `WriteFile` instead of leaving it as created because mvmd now commits a file whole in a running guest, which ADR 0020 rejected live updates for want of; it polls with `get` because the Node authorizer allows no watch.
- The agent acts on the probe results because mvmd acts on none (mvmd ADR 0057 at `eebb760d62370c1ebf49bb86c5a9413d76c71650`), and does it through the restart it already has so that a liveness failure and an exit share one backoff, one count and one rule for `Once`. It reads the results at the resync because it watches the gaon API and not mvmd's events, which costs up to one resync of delay in `Ready` and in a liveness restart.
- The grace period is always set, and never left unset, because mvmd documents no meaning for an unset one (mvmd `eebb760d62370c1ebf49bb86c5a9413d76c71650`), and gaon's `0` must reach mvmd as `0` and not as the absence of a value.
- The epoch in the mvmd identifier makes rebinding to the same node a replacement rather than a reuse, so state of an older epoch cannot carry into a newer one.

## Open questions

- **Entrypoint record across a start:** mvmd's documents do not say whether the console log an entrypoint's record is answered from is cleared when a MicroVM starts. The agent treats a clean record equal to the one it read at the MicroVM's previous exit as a failure, so a stale record cannot end the restarts; a MicroVM switched from `Always` to `RerunOnFailure` whose entrypoint keeps exiting cleanly is therefore restarted, at the backoff.
- **Node addresses:** which addresses the agent reports.
- **NetworkPolicy and mvmd's policy:** the create-time policy the `default` plugin returns (empty without `--egress-prefix` and `--ingress-prefix`) is mvmd's, and the nftables rules of `Enforce` are applied on top of it. Whether a NetworkPolicy that allows what that policy blocks should open it is not decided: today it does not. The `forward` hook does not see traffic that does not cross the Node's router, such as two MicroVMs on one bridge if mvmd does not route it, which is mvmd's to say. A MicroVM has no limit until its `status.addresses` is written, so it is unrestricted by NetworkPolicy until the round after that.
- **LAN failover and announcement:** while the answering Node's agent is down and its MicroVMs still show ready, no Node answers for the LAN address. The plugin sends no gratuitous ARP or unsolicited neighbour advertisement when it takes an address, so a LAN neighbour that cached another Node's answer keeps it until it expires. Neither is decided.
- **Conntrack mark and a MicroVM calling its own Service:** the plugin takes the whole conntrack mark, not a masked bit, so it cannot share the mark with another user of the Node. A MicroVM that connects to a Service it is a backend of is translated to itself without masquerade; what the guest does with a connection from its own address is not examined. Neither is decided.
- **Services without a local MicroVM:** a Node that runs no MicroVM never answers for a LAN address, so a cluster whose MicroVMs are all stopped announces none.
- **Leaked disks:** the `local` storage plugin deletes a disk only for a Volume it sees being deleted with its finalizer. A `volume-` disk whose Volume the API no longer has, or never pinned to this Node, is not found and not deleted.
